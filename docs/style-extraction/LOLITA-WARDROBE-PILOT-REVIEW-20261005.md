## 结论

**独立 Lolita 衣装方向有可见效果，但保留原衣与裁剪保护仍存在失败。实验采用的是候选 v2，不能直接算作当前生产原版已验证。建议先修保留条件的实际请求，再做小范围复测，不直接采用 v2。**

24张图真实存在且能解码；24条 prompt 的全文哈希全部一致，样本ID无重复，状态均为 success。GPT图均为1024×1536；Gemini图为1696×2528。当前生产10个衣装模板的文本hash与运行冻结记录一致，未被候选覆盖。19个衣装 unittest 复跑通过；这只能确认代码契约，不能消除在线失败。

## 结果报告需要修正的地方

1. **C06“标签互换、分数不可用、裁剪保护成立”与原始证据不符。** `scores.json` 中两通道C06的 `assignment`/`blind` 都是 A=on、B=off，`images.A`也确实指向lolita文件。原始响应给A衣装4分、描述领口/蕾丝/胸衣，并给保护fail；B为0分、描述无相应服装或普通上衣。`scores-unblinded.json`的per_role与此一致。不存在报告声称的证据对调。衣装4分与裁剪fail分属两个维度，可以同时成立。原报告§1、§5.3、§6对C06的判断应撤回。
2. **不能说v2使C02“从改不动变成功”。** 本轮没有生成生产原版on的图，只生成off与候选v2 on。文本审查发现原版矛盾，不等于实测原版一定改不动；只能说v2在本例表现为目标改款。
3. **不能确认内容过滤只由评分文本导致。** 简短探针能看同一图，支持任务/措辞会影响过滤的推断，但没有相同端点、图片组合、请求形态下的单变量排查，且过滤响应本身没有说明准确触发项。“被拦的是评分提示词文本”写得过强。
4. **视觉调用超过约定上限。** 16个计划评分槽位，其中6个另用gpt-4o重试，实际评分尝试22次；另有两个vision-probe文件合计5次探针，因此可从记录确认至少27次带图尝试（不含其他底层重试）。这是新增评估请求，不能仅视作网络重试。原报告诚实披露22次，但仍超任务书16次限制。
5. **评分汇总的调用数口径不一致。** `scores-unblinded.summary.calls_total=16`是评分槽位数，`scores.visual_calls=22`才包含第二轮尝试；`model_usage`只计最终槽位归属而非所有尝试。11次最终成功、5个最终失败槽位，与22次尝试不矛盾，但应改名或并列注明。评分槽位覆盖9/12 case/channel组合，不代表9组合全部保护项通过。
6. **可复现证据仍有缺口。** 生图prompt全文已保存；评分文件保存prompt hash、图片路径/标签和raw响应，但未保存完整实际messages/评分请求正文。可以核对本地映射一致，不能独立还原图片内容块的真实发送顺序。后续应存不含凭据的实际请求快照。

## 下一步建议

生产原版、测试候选v2和下一版必须分开记录。不要因为改款成功就把v2整体写回。

优先把“衣装是否可替换”确定为提交时的结构化授权：区分源服装事实、用户强制保留与已有衣装。明确保留、或fill_missing且已有服装时，实际请求中省去不适用的整套Lolita设计块；不能只再加一条“设计块优先级较低”。识别过程需支持真实分析输入及用户语言，不能靠几个英文关键词冒充通用解析。修订/审计沿用有效授权快照。

裁剪要求应成为独立构图约束；C06只允许画已授权裁剪内的细节。复测至少覆盖C03/C04/C06，并保留C01/C02的正向回归。具体新请求数量另定，本次复核没有追加生图、评分或费用请求。

保留原图、原始报告与评分，不用“误判”清掉真实的保护失败。下一轮预算需在程序层计入成功/失败/重试/探针，并在上限前停止。
