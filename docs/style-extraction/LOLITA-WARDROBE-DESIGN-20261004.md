# Lolita 衣装风格提取与应用方案

日期：2026-10-04。状态：代码与历史实验研究、设计建议；尚未实现，也未进行新的在线提取或生图验证。

## 1. 结论与目标

建议增加独立的「衣装风格」控制层，与「绘画风格」可组合。复用多图提取的迭代编排、请求封装、缓存、断点、版本、测试产物和报告；衣装模式使用独立的提取提示词、结果结构、引用角色和评价标准。

目标行为：

- 只写「画一个长发少女」时，选择 Lolita 衣装即可补全一套协调的 Lolita 穿搭。
- 源图或分析描述已有非 Lolita 衣服时，可明确授权将其改为 Lolita 服装。
- 更换衣装不更换人物的年龄、脸、发型、发色、瞳色、体型、动作、场景和画幅。
- 同一衣装规则可以配合不同绘画风格；参考衣装是照片时，不因此把动漫人物改为照片画法。

这里的“提取/训练”是多轮视觉分析与提示词修订，不是训练 LoRA 或模型权重。现有 wardrobe 的产物也不能作为服装模型训练完成的证据。

## 2. 现有 wardrobe 的形成过程与证据

现有条目是 `cute-lingerie-wardrobe`，不是一个通用 wardrobe 模式开关。

1. 数据集：`data/style-learning/cute-lingerie-wardrobe-20260926/metadata.json` 记录从本地素材筛出 12 张参考，角色、配色与姿势有变化，以成套衣物、连接结构、花边、层次及材料为观察目标。`README.md` 明确把它定义为衣装主题数据集，而不是普通艺术画风数据集。
2. 输出：`conf/config-styles.json` 及子模块版本化文件中保存完整/压缩提示词、八字段画法短版、参考图、生成条款与修订条款。最关键的换装授权在 `generation_clauses`，不是八字段短版。
3. 测试：`data/test-result/20260926/cute-lingerie-wardrobe/manifest.json` 固定了棕发紫眼、25 岁、坐在书房木椅上的测试主体，同时明确允许改变其原服装。历史报告记录 Gemini 直出和 GPT 首图成功；完整参考图送 Gemini 重绘时出现银发、红眼、白色背景及武器泄漏。
4. 收敛：参考图从带无关武器的 `06-blue-white-fullbody.png` 换为 `04-white-bridal-set.png`；设置 `skip_repaint=true`、`repaint_reference_mode=none`、`skip_identity_refine=true`，保留首图。相关代码提交为 `40fa0c8`（2026-09-26）。

依据：`docs/gpt-image-tid-style/CUTE-LINGERIE-WARDROBE-20260926.md`。

当前检查到的文件中没有该条目完整的逐轮 `style_iter_result.json`；不能据此声称它由今天的多图画风提取 Tab 自动训练了若干轮。能确认的是：筛图、衣装专用条款、通道实验及运行策略落地。

其成人年龄条件属于原条目的具体用途，不能照搬成普通 Lolita 日常衣装的触发条件。Lolita 衣装不应改变角色年龄，也不应将服装名称解释为人物年龄。

9 月 28 日“安全替代”测试删除了原换装要求并保留礼服；这些成功结果不能证明原 wardrobe 换装成功，也不能证明未来 Lolita 方案已有效。

## 3. 当前链路有哪些冲突

| 位置 | 已有行为 | 衣装模式需要的区别 |
|---|---|---|
| `prompts/style-iter-common.md` | 只提画法、排除具体内容；要求 80% 共性 | 允许提取衣物设计语法与搭配关系，排除人物与画法 |
| `prompts/style-iter-variants.md` | 八字段短版禁止 clothing/scene nouns | 单独派生衣装短版，不进入画法短版校验器 |
| `utils/style_gpt.py` | `dress/skirt/outfit/costume` 等是泄漏词 | 保留普通画风规则；新增衣装字段与校验契约 |
| `utils/analysis_gen.py:build_first_pass_request` | GPT 分析链追加 `generation_clauses` | 可用作原型接入口，但独立记录衣装来源与授权 |
| `utils/styles.py:build_ref_gen_params` | 通用组装未读取 `generation_clauses`；参考优先可用八字段短版替代完整说明 | Gemini 等入口需显式注入衣装授权，避免换装要求丢失 |
| `prompts/style-ref-image.md` 等 | 参考图仅供画法，明确禁止取衣服设计 | 给衣装参考单独的角色声明 |
| `modules/image_generation/gpt_image2_tab.py` | 使用通用画风组装，不能假设分析链的附加条款会自动生效 | 所有承诺支持的入口走同一衣装组装逻辑 |
| `modules/image_analysis/style_analyzer.py:_generate_test_image` | 固定三路；完整画风图重绘；画幅可跟随测试参考图 | 衣装模式自定测试分支，画幅由测试任务决定 |
| 身份审计 | 把 outfit design/colours 作为稳定身份字段；对实际首图混合 prompt 取事实 | 传入已消解原服装冲突的目标规格 |
| `skip_identity_refine=true` | 记录身份审计，但跳过整个身份回改及该处分歧拦截 | 不只豁免服装，也会影响发色等保护，不适合作为长期方案 |
| 质量/最终审计 | 第三张图是画法参考，考察脸、眼、发束、颜色与材质画法 | 衣装图不能占据画法参考角色；衣装另审 |
| 色调校准 | 可将画风参考作为色调目标 | 衣装参考不得自动成为全图色调目标 |

最终审计已有 `authorized_changes` 输入，可复用授权传递机制，但不能把衣装参考的画法误当作画风目标。单靠追加一句“允许换装”，不足以清除所有阶段的歧义。

## 4. 建议的产品行为

两个选择：绘画风格（例如水彩/某画师提取）＋衣装风格（例如 Lolita）。在现有选项行内紧凑放置，遵守 AGENTS 的窗口与两行 GPT 参数约定，不新增常驻大行。

建议先提供三种策略，内部使用明确枚举，不假装数字强度等于模型可控权重：

| 策略 | 原提示词未写服装 | 已写普通服装 | 明确要求保留原服装 |
|---|---|---|---|
| 补全 `fill_missing` | 设计 Lolita 穿搭 | 保留已有要求 | 保留 |
| 改款 `reinterpret` | 设计 Lolita 穿搭 | 改成 Lolita，尽量沿用用户指定配色/标志性元素 | 保留 |
| 替换 `replace` | 设计 Lolita 穿搭 | 替换衣物类别与结构 | 保留；需额外明确授权才能解除 |

用户举的两个例子最适合默认 `reinterpret`：选中即偏向目标衣装；无衣服描述时补全，有普通衣服描述时允许改款。用户明确提出“仍穿校服、只加少量 Lolita 元素”应作为本次约束，不能被预设静默覆盖。

需要分开处理：衣物类别/裁剪、衣物颜色、标志性配饰。没有规定配色时根据角色和场景选一套；已经规定红黑时优先沿用红黑，不因训练集中粉色多就染成粉色。

## 5. Lolita 应提取的内容

V&A 将 Lolita 描述为有多个分支的日本街头服饰文化，并列出蕾丝、荷叶边和头饰等搭配；它不是一个特定绘画媒介，也不等同于 cosplay。来源：<https://www.vam.ac.uk/articles/lolita-fashion-japanese-street-style>。

BABY 官方的搭配页将 jumper skirt、blouse、发饰、袜子和鞋作为组合展示，支持把它设计为整套穿搭规则，而非给普通裙子加几个蝴蝶结。例：<https://www.babyssb.co.jp/series/20260410_stripe-julia-frill/>。这些来源说明类别与搭配，以下模型控制方案是本项目设计建议，不是来源验证过的生成效果。

建议先做 `lolita-sweet-wardrobe`；若素材实际偏古典或 Gothic，应分别命名和提取。不要把不同分支最醒目的元素全强制叠在一起。

建议衣装输出维度：

1. **轮廓**：有结构的裙摆体积、腰线与上身/裙摆比例；区分钟形与 A-line 等可选形态。不要靠改变腿长或体型制造裙型。
2. **衣物组合**：OP（连衣裙）或 JSK（背带裙）＋衬衫等备选组合；衬衫不是所有款式的强制项。
3. **结构与层次**：领口、袖型、肩带、腰带、抽褶、裙片、裙撑与外裙的关系；不凭照片声称看到了被挡住的裙撑。
4. **装饰语法**：花边宽度与层次、荷叶边分布、蝴蝶结大小/位置、印花重复尺度、花纹沿衣片和下摆的位置。必须说明“在哪里、怎样连接”，而不仅是“很多蕾丝”。
5. **材质设计**：布料挺度、垂感、透明内层/不透明外层的组合；画出材质的笔触与光照由绘画风格负责。
6. **搭配关系**：头饰、鞋袜、包与主裙的色彩呼应、装饰层级和使用条件。新增配饰不得移走手中已有道具。
7. **可变范围**：颜色、图案、裙长、袖长、装饰密度、分支差异；必须允许生成不同的衣服。
8. **排除与反例**：普通薄 A-line 裙上只加蝴蝶结、女仆围裙、舞台偶像服、夸张洛可可拖尾等相邻类别，不能自动算符合目标；以目标子型和实际结构判定。

“近膝裙长、蓬松裙型”等可作为首版产品默认值，不能未经样本核对就宣称是全部 Lolita 的必要条件。

## 6. 提取流程如何复用

保留当前 worker 的多轮共性→差异对账→局部细化→终审→模型派生→测试/报告；增加 `extraction_kind=art_style|wardrobe`，历史缺失时默认 art_style。

衣装模式替换每个阶段的提示词，而不是只改第一次 common 提示词；否则 reconcile、final-review 或 variants 会再把衣装内容清掉。

建议新增模板组放 `prompts/wardrobe/`：common、reconcile、refine、local-extract、local-merge、final-review、variants、reference-role、comparison、audit/correction。当前研究不创建这些运行模板，避免尚未验证的规则被当作已上线能力。

### 数据与证据

- 首版建议 12–20 张同一衣装分支参考：多角色、多发色、多个画师/摄影来源、不同衣服与动作；这是试验预算建议，不是已验证最佳数量。
- 服装应有足够的全身/裙摆可见样本与结构细节。可以混用实物搭配、商品图和插画，但记录来源类型及看不到的部分。
- 以“类别准确、衣装可读、结构完整、覆盖多种款式、人物/背景干扰低”筛选，不再用“画法一致性”作为关键入选分。
- 原 80% 共性可作为初筛思路，不能把 80% 以下的正确款式删掉。改为核心不变量＋条件组合＋可选变量，并记录每个特征的支持图编号、可观察样本数与反例。
- 同一条蕾丝裙的多张近似图不能当作多种独立设计支持；去重并记录同款组。
- 固定头发/脸裁剪改为上身、领袖、腰部、裙摆/下摆、鞋袜、饰品。先保留整图联系；多人和偏置人物可手动指定区域，找不到时标不可观察，不强行分析背景。

## 7. 输出数据与生图编排

长期建议单独配置衣装预设，统一工具读取，避免占用艺术画风配置里的八字段。示意结构如下，全部是建议字段，当前代码尚不支持：

```json
{
  "kind": "wardrobe",
  "name": "lolita-sweet-wardrobe",
  "version": 1,
  "application_policy": "reinterpret",
  "core_rules": [],
  "outfit_combinations": [],
  "conditional_rules": [],
  "variable_traits": [],
  "palette_policy": "keep_explicit_else_coordinate",
  "preserve_features": ["identity", "age", "hair", "eyes", "body", "pose", "scene", "aspect"],
  "prompt_full": "",
  "prompt_short": "",
  "generation_clauses": [],
  "continuity_clauses": [],
  "reference_images": [],
  "evidence": [],
  "review_profile": "wardrobe-v1"
}
```

推荐编排：

`原始分析/用户输入 → 本次目标内容规格（合并衣装授权） → 模型专用 prompt → 首图 → 衣装/人物审计 → 可选画法重绘 → 人体/衣装/画法终审`

原始分析描述仍然忠实记录源图，不为换装改写成假分析。另存本次 `resolved_generation_spec`，区分保留锚点、可修改范围、目标衣装、色彩条件与角色作用范围。后续审计用本次目标，而不是从同时含“原校服”和“换 Lolita”的长 prompt 猜测优先级。

首版可直接由确定性模板追加衣装规则，减少一次 LLM 调用。若需要精细改款，再增加有缓存的 outfit-plan 步骤；该步骤只生成衣装设计，不补写人物或场景事实。短提示词必须保留换装授权与裙型/搭配，不得压缩成“cute, lace, ribbons”。

多图明确分工：内容图管人物与场景；衣装图管类别、结构与穿搭语法；画法图管线条、着色与完成方式。顺序由实际请求与图角色映射共同记录，不能沿用“最后一张总是画风图”的单参考假设。

推荐先比较文本衣装规则与衣装裁剪参考两条路径。参考图只补设计证据，不自动高于用户衣物配色，也不改变画幅。重绘优先采用当前图＋文字或当前图＋独立画法参考；衣装参考不默认再次送入完整画风重绘。原 wardrobe 的失败只说明其特定实验有泄漏，不能证明所有 Lolita 参考重绘都必然失败。

换装成功后重绘应保护“新衣装”作为连续性锚点；若专门在重绘阶段换装，必须使用独立换装请求，不能与默认 outfit lock 同时发送。身份检查保留发色、瞳色等门禁，只豁免授权的旧衣装字段。衣装不符合目标时单独失败，不因跳过身份回改被掩盖。

参考用于服装不等于可供色调校准。色调工序只读独立画法/色彩目标；没有该目标时关闭该步，而不是拿衣装图的粉色或白底校准全图。

## 8. 验证设计

初始对照：A 只写 `Lolita fashion`；B 结构化衣装规则、无衣装图；C 同规则＋衣装裁剪参考。采用相同模型参数和固定测试输入，所有分支保留实际 prompt、图角色、图片/模板 hash、成功/拒绝状态；失败结果不能从统计中消失。

第一轮先覆盖三个触发：无衣服描述、明确非 Lolita 衣服、明确保留原衣服。选择候选方案后再覆盖：指定红黑配色、坐姿、胸像、多人（逐人指定）、跨绘画风格、首图后重绘、后处理后最终图。至少在 GPT 和 Gemini 两个目标入口分别验证；不能只测试提取 Tab 再声称所有 Tab 支持。

测试无需机械地对每个候选都跑当前三路完整画风重绘；先确认衣装生成有效，再做候选重绘保留对照，复用已成功的首图避免重复收费。每个关键组合重复至少两次仅供发现波动，不能称为统计稳定率。

衣装独立量表：目标类别辨识、轮廓与层次、衣物连接合理性、装饰位置语法、整套搭配、可变设计能力。另审人物保持、场景/画幅保持、原衣服是否残留、参考脸/发色/道具/画法泄漏。

当前 `style-comparison-v2` 的十二项主要评价画法，并把参考服装替换主体当作泄漏；衣装授权场景必须改变比较契约。CSD、Gram、AdaIN、LPIPS 可作为非目标画法变化的辅助观察，不能充当 Lolita 类别正确率或衣装连接正确率。不得把人工/模型量表写成客观相似百分比。

胸像中的鞋袜和被遮挡的裙撑应为不可观察/不适用；不能为通过评价强制把人物变成全身或补出被挡住的结构。

工程回归重点：普通画风缺省行为不变；所有承诺入口都有换装授权；衣装词不送入八字段画法修复；原分析不变；明确保留服装和指定色彩有效；修订不恢复旧服装；衣装图不成为画法/色调/画幅目标；断点记录目标规格且旧付费成功调用仍可复用。

## 9. 推荐落地顺序

1. **小范围原型**：独立 Lolita 衣装模板＋三种策略＋两个通道共享的 prompt 注入；文本优先，保存可审查请求与本次目标，不依赖衣装参考图。验证两个用户目标是否实现。
2. **衣装提取模式**：复用现有迭代/缓存/版本/报告框架，接入衣装模板、数据结构、局部区域与专属量表；从选中版本导出衣装预设。
3. **组合与完整工序**：独立衣装/画法选择、多图角色、定点审计修订、最终连续性与色调隔离；覆盖 GUI、无头 CLI 与其他承诺入口。

不建议直接复制旧 wardrobe 的 `skip_identity_refine=true` 作为长期答案，也不建议为了让衣装词通过而全局放宽艺术画风校验。旧条目可保留兼容，新增预设逐步迁移；只改运行配置不足以实现这些契约。

本次仅新增研究文档，未修改运行代码、提示词或配置，未调用付费分析/生图接口；无需为本文重启 app。未来修改 Python 后按项目要求重启 app。
