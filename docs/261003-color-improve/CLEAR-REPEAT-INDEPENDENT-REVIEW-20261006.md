内容评审将部分跨图尺度差异当作单图 content fail，确有口径问题。但场景原文和 protected_facts 确实声明 fixed viewpoint/object scale，不能事后把全部要求解释为仅图内，或把所有构图差异改成 outline_only。下一版应分别评价单图事实、跨图混杂与颜色可判性；真实影响绑定面判断的尺度/光照差异仍记 substantive。当前冻结结果保持原样。

## 发现的遗留问题

1. **C 的回放不是完整正文。** 三张 C 的实参/冻结正文均为 4136 字符；回放保留前 4000 字符后加 TRUNCATED 标记，恰好截掉候选末尾部分保红/保护规则。`api_backend._generate_request_replay` 调用了面向日志的 `_sanitize_log_data`，导致回放同样截短。实际 `requests.post(json=payload)` 使用原 payload，保存器未就地修改；代码和实参支持完整发送，但截断回放不能独立逐字证明完整线上请求。下一轮前应区分日志缩略与完整脱敏请求快照，并测试长文本保留；不要补图、伪造完整历史回放或覆盖原证据。
2. **预算摘要硬编码错误。** RESULTS anomalies 写“冻结包预算10次之外另有1次”，实际冻结9、补发1、总发送10；RUN-REPORT 另将读取超时描述成 S1-A 后端崩溃丢图，本轮槽位是 A1。这些是共享报告函数残留的旧实验措辞，后续应从 pack/ledger/错误类型生成。九槽位、三组评审的标题也应动态生成，避免“十槽位/四组”等旧标题。
3. **绑定观察数量写错。** DS 报告写21条，实际九图每图三个表面，共27条，全部 ID 覆盖。9对18个输入项引用的是9张不同原图，不能读成18张新图。
4. **灰混杂判据仍不足。** 把更深红当作更清楚，容易把明度或保红作用计入清色效果；下一版须允许“保红改善但去灰不确定”，分别评价蓝/红表面，而非只给整组单一优胜 ID。

1. 先离线修长文本回放、动态预算/异常文案及下一版评审轴；测试后再准备新冻结包。当前报告追加勘误，不覆盖原始 JSON、盲评与图片。
2. 将清色候选保留为研究版本，记录“保红有信号、去灰尚不确定、可能伴随变深”。不直接覆盖生产模板，不继续单纯叠加形容词。
3. **二阶段主次关系应优先推进。** 选择本来就有两个可比大面积表面的场景，固定同一色板/绑定、关闭 tone，只改变宽松主次指令；不通过增加物件、扩大物件或固定百分比实现。辅助色绑定另测，以免同时改变两件事。先冻结离线方案，再明确有限预算交接；本复核未发起或授权新的收费轮次。
4. 若另做清色迁移验证，优先同色板新场景，以固定色板基准对比候选，独立记录保红、灰混杂、明度。跨色板前须将候选中的 blue/red 和保红句按所选色相参数化，不能把红蓝专用措辞原封不动套到其他色板。
5. 第三阶段保持为既有材质/光线、知觉突出/后退、画风迁移和重绘保色。情绪/季节仍在用户选择后的 refine 阶段添加，不覆盖固定色板。全程禁用本地蒙版羽化、图片叠加或局部贴回。
