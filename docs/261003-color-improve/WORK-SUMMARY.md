## 三、做了什么

### 第 1 步：把原计划书改成本项目能跑的版本

`docs/261003-color-improve/AI_Color_Knowledge_Extraction_Workflow-v2.md`（58 KB）。
原计划书是通用模板，与本项目实际能力对不上，改造集中在三处：

- **现实核查**：目标 PDF 是**纯扫描件**（`/Font` 出现 0 次、150 个 `/DCTDecode` JPEG、
  无文字层），所以必须走视觉链路，原文里"先抽文字层"的路子整条不成立。
- **明确验证范围**：追加 §6.0「哪些页要跑、哪些页不跑」。原计划书把 150 页当默认全量，
  实际花钱的视觉提取第一遍只 **55~56 页**（理论 7 + 案例首页 32 + 笔记 16），
  绘画过程页"不建议跑"（`process_points` 无下游消费者）。
- **逐条回应审阅意见**：`gpt-6-sol` 审出 26 条，附录 D 逐条回了 24 条。

### 第 2 步：全书 150 页逐页转录

按 13 批推进，每批 10 页，**每批结束做一次回头检查**（跑自带抽检 + 一次视觉接触表比对），
发现问题当场修再继续。

- 早期页（PDF 8–37）用 `配色要点` 表收尾；
- 从 PDF 38 起换成了 `本页直接给出的做法（原文，未加工）` 表，
  只放书里的原话，不再夹自己的英文改写。

### 第 3 步：做成按章分页的站点

- 按**白缝**切配图（不是连通域），判据用**最长连续笔画**而不是行墨密度，
  再加三条护栏（直线过关者须 ≥150 px、矮块须 colorful ≥0.25、整页插图不抠），
  抠出 431 张配图。
- 章节划分与逐页标题落在 `structure.json`，站点从它生成（可反复重建）。
- **2026-10-02 改版**：扫描原页不再占右侧半屏，改成页眉里一个 `扫描原页 ↗` 小链接，
  正文单栏铺满。

### 第 4 步：抽成结构化配色知识

新增 `utils/color_extract.py`，三块产出：

- **条款库**：解析我在页面里写的「本页直接给出的做法」表（95 页有），
  按**书自己的分类体系**归类（主轴取自 PDF 146 那篇笔记的五步流程 + 两条注意事项，
  再补光效 / 材质 / 排列 / 构图 / 面积 / 知觉）。
- **案例配色库**：31 个 `case_analysis` 页的 5 色主色调 + 色相/色调平衡的原文结论 + 面积占比原句。
  （全书 `case_analysis` 页共 **32** 个，PDF 116《伯劳鸟 / 鸟》是"两作同页对照"页、没有主色调栏，
  所以进库的是 31 个。）
- **词表**：题材五切入点（p10）/ 情绪环状模式（p53）/ 形象坐标（p74）/ 味觉（p60）/ 音乐（p137）。

### 第 5 步：做一个能用的注入口

`python -u tools/color_knowledge.py color-block --query 紫藤` 输出一段
**可直接追加到生图请求**的文本块：作品名与主题、5 色色板（带 NCD 坐标或"固有名"标注）、
色相/色调范围的原文结论、面积占比原句、该作品自己版面的规则，末尾附五步法核心条款。

`--query` 依次尝试 slug → 作品名 → 画师 → 色名 → 标签，**并把命中理由打印出来**。

## 五、过程中修掉的问题

### A. 代码缺陷（4 个）

1. **`_md_to_html` 有真死循环** —— 某行没被任何块级分支吃掉时不推进游标。
   PDF 15 的 130 行色表触发过一次，站点构建卡死十几分钟。
2. **抽检脚本自己的 bug** —— 去 hex 的正则被尾空格挡住；体量检查写在 `palette:` 分支里，
   导致笔记 / 理论 / 封面整类页面永远查不出来。
3. **标题兜底命名的三条约束**（都是实测踩出来的）：
   ① 锚点只用 `case_analysis` 作品页（笔记页插在中间）；② 只在同章范围内找
   （PDF 67 属第 5 章，差点挂到第 4 章）；③ 排除章节封面（封面名字是画师名不是作品名）。
4. **标题优先级** —— 最终定为「转录时写的 meta > `structure.json` > 兜底规则」。

## 七、口径与边界（读产出时要知道的）

**1. 正文是逐字照抄，色板行与配图行不是。**
页面里的 `色板（N 色）：…` 是我**对着印刷色块目测的读数**（那些色块没有文字标签），
`配图：…` 是我对例图的**归属判断**。这两类只作速览，要真实色值必须走
`measure` 对扫描页实测。

**2. 条款分两级可信度。** 每条带 `evidence_type`：

| 值 | 含义 | 量 |
|---|---|---|
| `stated` | 表里那列是**书里的原话** | 386 |
| `derived` | 来自早期页的「配色要点」表，**混了我自己写的英文对照** | 44 |

下游要严格只用原话时，过滤 `evidence_type == "stated"`。

**3. 案例色名不做就近映射。** 书里混用「固有色名」（紫藤色）与「色彩系统名」（蓝紫色），
PDF 34 的笔记已明说。能对上 130 色表的补坐标，**对不上的显式标为固有名、其余字段留空**。

实际结果：155 格里对上 **58 格（37%）**，固有名 **97 格 / 83 个不同名字**
（朱红色、雾蓝色、薄雾蓝色、雪白色、灰粉色、焦黑色、锦葵粉色、铬绿色、烟竹色、黑茶色……）。

**4. `process` 单独分出 43 条。** `case_process` 页的表格是"加背景山""人物底稿"这类
逐步操作记录，**不是可复用条款**，混进规则清单会被下游当成配色指令。

## 八、已知遗留 / 下一步

### 没做的

1. **案例配色没有真实色值。** 主色调栏只有色名，能对上色表的 58 格有标称值，
   其余 97 格是固有名。要拿真实色值得对扫描页跑 `measure` 实测。
2. **`--color` 只在命令行可用**，没接进 `modules/image_analysis/` 的生图链路。
   按项目约定改 `utils/analysis_gen.py` 的请求组装要补回归用例，且**改完必须重启 app**。
3. **`utils/analysis_gen.py` 的注入点未落地。** 之前定过三条：`color-*` 画风条目 /
   `--color <slug>` / `--tone-reference`。其中第一条已否掉（缺 `prompt_gpt` 的画风条目
   在四种参考图模式下都返回 `('', '', [])`，贡献为零），后两条没接。
4. **原计划书里的 tone 目标** —— `utils/post_process.tone_calibrate` 是**均值级**幂律亮度匹配
   + HSV 饱和度按比缩放，只取参考图的 LAB L 均值 / HSV S 均值；`tone_target` 在
   `post_process.py` 里**完全不读**，只读 `reference_path`。要接得先想清楚。
5. **过时文件没清**：`data/color-knowledge/` 里的 `color_theory.json`（16 条）、
   `lighting_rules.json`（7 条）、`knowledge_index.json`（7 页）是**早期 7 页样本时建的**，
   已被 `color_clauses.json` / `palette_library.json` 取代。留着是历史记录，
   新代码不该再读它们。

### 建议的下一步（按性价比排）

1. **拿 `measure` 给 31 个案例实测色值**，补进 `palette_library.json`
   （本地跑，几秒一页，不花钱），顺带能验证"印刷色 vs 标称色"的偏差。
2. **把 `color-block` 接进生图链路**，先做 CLI 侧端到端验证，再动 GUI。
3. **把 430 条条款按"可执行"筛一遍** —— 现在有些条目（尤其 `other` 那 57 条）
   是描述性的，不是指令性的，接提示词前要人工过一遍。
