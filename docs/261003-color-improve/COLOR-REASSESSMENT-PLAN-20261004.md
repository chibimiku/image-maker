## 1. 本轮修正后的验收目标

配色方案的目标是**让画面呈现指定的一套色彩**，不是改善画质，也不要求比基线更好看。因此本轮：

- 只判「指定颜色是否出现、基调/辅助/强调是否按方案分工、是否落在指定区域、冷暖是否正确、是否混入大块违背方案的颜色、受保护颜色是否保留」；
- 不作美学排名，不用总质量排名、旧评分或旧赢家作为判据；
- 内容与画法单列，配色符合不抵消内容失败，觉得不好看也不判配色失败；
- G0/G1/G5/G6 与 T0 是**未指定色相或完全无方案的对照**，不要求它们符合其他组的方案条款；
- 「冷蓝 + 红」只是未来目标的例子，本轮没有任何组要求这一组合，因此不拿它验收本轮图片。

## 3. 计划（固定后不再改）

### 3.1 分块

39 张按「套件 + 方案 + 轮次」排序，**同方案三张永不拆块**，每块最多两个方案、共 6 张图（配对的方案文本长度相近）。块数 7：

| 块 | 内容 |
|---|---|
| reassess-01 | G0（无方案）×3 + G1（只有内容保护）×3 |
| reassess-02 | G2（春绿短版）×3 + G3（春绿完整）×3 |
| reassess-03 | G4（柔蓝完整）×3 + G5（只调明暗层次）×3 |
| reassess-04 | G6（只调彩度焦点）×3 + G7（暖柔春景）×3 |
| reassess-05 | T0（同轮无方案）×3 + T1（冷色调一句）×3 |
| reassess-06 | T2（冷色调更强）×3 + T3（暖色调对称）×3 |
| reassess-07 | T4（点名 teal/slate blue/cool grey）×3 |

同一块内每张图**各自携带自己的逐字条款与方案标签**，块与块之间不重复方案。方案文本长度不同这一差异无法隐藏，如实记录为限定。

### 3.2 调用预算

- 计划业务调用 **7 次**，授权上限 12 次，本轮硬上限 10 次（留 3 次缓冲）。
- 缓存：命中同一协议 hash 的记录直接复用，不重复收费；`vision-calls.jsonl` 记每次业务调用，`reassess-failures.jsonl` 保存失败记录。
- 失败策略：**连续两次业务调用失败即停止并报告**，不自动换模型、不扩大预算、不做业务级重试（底层 HTTP 重试由客户端计数，另记）。
- 不新增生图、编辑、重绘；不重试 GPT 生图；不改生产 GUI、全局配置、画风固件或质量门禁。

### 3.3 评价模型看到什么

给评价模型：逐字方案条款、保护块、受保护颜色清单、内容与画法检查项、方案说明性标签（如「春绿 · 完整版」）。
不给评价模型：旧评分、旧赢家/排名、旧报告预期结论、协议分组标签（G/T 编号）。

每张图随附一张**下半身细节裁剪**（同一图下方 40%~95%），用于判断厚底鞋、蝴蝶结与肢体可读性；协议明确规定细节裁剪不得用于判断画幅或区域布局。

### 3.4 输出（实际落在 `color-reassessment-v2/`）

- `reassessment-protocol.json` / `reassessment-protocol.md`：冻结的协议、分块与 `protocol_amendment`（失败块从 6 张/块细化到 3 张/块的补跑记录）。
- `vision/reassess-NN.request.json`：实际评价请求全文（system + user + 图片清单与 hash）。
- `vision/reassess-NN.raw.txt`：模型原始响应；`vision/reassess-NN.json`：结构化记录（含 `json_repair`、`recovered_offline` 等标记）。
- `per-image-evaluations.json`：每张图的结构化评价。
- `reassessment-summary.json`：按方案汇总的符合度、重复一致性与偏差。
- `conformance-review.html`：可离线浏览的逐项评价页面（图内嵌，无外部依赖）。
- `reassess-failures.jsonl` / `recovery.json`：失败记录与离线回收记录，均保留。
