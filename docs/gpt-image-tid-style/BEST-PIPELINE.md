# gpt-image-2 画风生图 · 当前最优解与完整工作流

> 这份是操作手册（要改 prompt / 调指标口径先看 `README.md`；要只看首图提示词看 `BEST-PROMPT.md`）。
> 全部结论都有实测数据支撑，索引在每节末尾。

---

## 一、当前最优解（一句话）

**分析产物出两档字段 → gpt-image-2 用 `prompt_gpt` + 短内容锚 + 画风参考图出首图 → Gemini 重绘（v5 保守修复固件）→ 结构线叠加 → （头发/脸/裙子糊时）该区域局部重绘 + 羽化贴回。**

每一步都独立可选，GUI 里每道工序一个勾选框；缺哪一步不会毁掉前面的结果。

## 二、各道工序与实测收益

| 工序 | 做什么 | 实测收益 | 代价 | 出处 |
|---|---|---|---|---|
| ① 画风短版 `prompt_gpt` | 把 11k 全量画风压成 8 字段 ≤680 字符 | 长文本会压住参考图：同 prompt 下参考图相似度 0.107 → **0.280**（短锚+排除句） | 无 | §4.5 / §4.18 / §4.19 |
| ② 内容锚字段 | 分析产物单独出 `gpt_image_prompt`（≤1400）与 `gpt_image_prompt_short`（≤500） | 15.6k 字符的现产物组合**直接断连**；1.8k 稳定；短锚 + 排除句把画风相似度翻倍 | 一次文本调用 | §4.16 / §4.18 / §4.19 |
| ③ 参考图角色排除句 | 明确"只借色调/渲染，不得搬参考图角色/发色/瞳色/服装/姿势" | 饱和度 44 → **25.7**（tid 参考图自己 25.0），画风相似度 0.107 → **0.323**；不再产出"粉发金瞳" | 无 | §4.19 |
| ④ 首图生成 | gpt-image-2，`medium`（不是 high）+ `1024x1536` + PNG | v6 模板 + high：中灰带 0.681、高光裁切 0.001%、骨架段长 145.5；`high` 会吃掉留白、水彩感变差 | — | §4.9 / BEST-PROMPT |
| ⑤ Gemini 重绘（v5 固件） | 保守修复 + 色彩匹配 + 线条连通 + 禁止凭先验补全 + 眼部保留式修复 + 主结构/次级笔触分级 | 头部 MAE 2.3~3.7（cel 旧固件是 6.5/**63.8**）、配色 0.97~0.99；**修掉了 v4 凭空补手** | 一次 Gemini 调用 | §4.14 / §4.17 |
| ⑥ 结构线叠加 | 抽长结构边 → 按局部色调整色 → 按强度叠回（纯本地，不调模型） | 骨架段长 **+6%（say-hana）/ +17%（noir）/ +22%（tid）**，端点密度最多 −16%，配色与饱和度几乎不动 | 几十毫秒、零成本 | §4.20 |
| ⑦ 局部重绘 + 羽化贴回 | 按区域（头发/脸/裙子/头部/上半身）裁切 → 放大 → Gemini 重绘（v5 固件 + 区域强调句）→ 羽化贴回 | **头发带**：段长 +6~22%、端点密度 −7~20%（noir 121.1→147.2、端点 18.8→15.0；tid 230.2→244.3） | 一次 Gemini 调用 | §4.21 |

**优先级（性价比从高到低）**：⑥ 结构线叠加 → ⑦ 局部重绘（头发糊时）→ ⑤ 全图重绘 → ② 两档字段（一开始就要有）。

## 三、完整工作流（素材照 → 成图）

### 步骤 1：分析素材照（分析 Tab，两个勾选都建议开）
1. 勾选 **服装搭配检查** + **去除照片风格**（Step 3 / Step 4），跑分析。
2. 产物四件套（同一目录、同一 base filename）：
   - `<name>.json` —— 含 `english_description`（给 Gemini 用）、`pixiv_tags`（内容锚）、**`gpt_image_prompt`**、**`gpt_image_prompt_short`**
   - `<name>-prompts.txt` —— Gemini 通道用（`--ar` + 画风 + 长描述）
   - `<name>-original-prompts.txt` —— 未 refine 版
   - `<name>-gpt-image-prompts.txt` / `<name>-gpt-image-short-prompts.txt` —— **gpt-image 专用两档，和上面的绝不混用**
3. 开关：`conf/config.json` 的 `enable_gpt_image_prompt_single` / `enable_gpt_image_prompt_short_single`（默认都 True）。

### 步骤 2：出首图（gpt-image-2 Tab）
1. 画风选 tid（或任意画风），**挂该画风的参考图**（`ref_image`，走 `/images/edits`）。
2. 提示词用 **画风短版 + 短内容锚**，并**带上参考图角色排除句**：
   ```python
   from utils.analysis_gpt_prompt import compose_gpt_image_prompt
   from utils.styles import style_prompt_gpt
   prompt = compose_gpt_image_prompt(style_prompt_gpt(styles, "tid"), gpt_image_prompt_short,
                                    style_ref_exclusion=True)
   ```
   经验长度：**总 ≤1,300 字符**画风最像；只求内容像可用完整锚（≤1,800）。
3. 参数：站点 `new.aigc2d`、模型 `gpt-image-2`、画质 `medium`、尺寸 `1024x1536`、格式 PNG。

### 步骤 3：后处理（同一个 Tab，每道工序一个勾选框）
| 勾选框 | 参数 | 什么时候勾 |
|---|---|---|
| ☑ **出图后立即重绘优化** | 模型 / 分辨率 2K / 比例 auto / 次数 1 | 默认勾（清线 + 提分辨率） |
| ☑ **结构线叠加** | 强度 0.50（0.35 更轻、0.7 以上偏硬） | 基本都可以勾，零成本 |
| ☑ **局部重绘 + 羽化贴回** | 区域下拉：**头发**（默认）/ 脸部 / 头部 / 裙子 / 上半身 / **整个人物** / **人物·保脸（手参与重绘）** / **人物·保脸保手（手保持原样）** / 整张；羽化 40~64 | 看哪块糊就勾哪块；头发最容易糊。只想修衣服头发、不想动脸 → 选「人物（不含面部）」 |
执行顺序固定为 **重绘 → 结构线 → 局部重绘**，结果列表里只出现最后一道工序的产物，中间产物写在日志里。

**区域说明**（实现在 `utils/post_process.py`）：

| 区域 | 覆盖 | 备注 |
|---|---|---|
| 头发 / 脸部 / 头部 / 裙子 / 上半身 / 整张 | 固定比例框 | 快、可预期 |
| **整个人物** | **自动检测的人物框**（GrabCut 前景 + 人脸锚点，外扩 4~6% 不切发梢裙摆） | 实测三族都框住全身：say-hana (82,7,1603,2528)、noir (47,0,1627,2468)、tid (108,0,1624,2450) |
| **人物·保脸（手参与重绘）** | 同一个人物框，**只把脸区排除**（反向羽化保留原像素），**手照常参与重绘** | 脸：Haar 优先，动漫脸检不到时从人物框上半部居中断定（约画面高度 20%）。人物区域都带手套状态条款（见下） |
| **人物·保脸保手（手保持原样）** | 人物框 + 把**脸和双手**都排除（手逐点保留原像素） | 手部框由 YOLO pose 的手腕/肘关键点推算（`tools/detect_hands_pose.py` 子进程 + `cache/hand_boxes.json` 缓存，戴手套也能找到）；检不到退回肤色色块 |


GUI 之外也可以走命令行（同一套实现，`utils/post_process.py`）：
```powershell
python tools/overlay_structure_lines.py --base <图> --strength 0.5 --out <图>-sline.png
python tools/local_repaint_composite.py --image <图> --region hair --feather 40 --scale 1.0 --out <图>-hair.jpg
python tools/build_gpt_image_prompt.py --json <分析产物.json> --tier short --show
```

## 四、成本与提示词长度（GUI 常驻显示）

价格来自中转站公开的 `GET https://new.aigc2d.com/api/pricing`（模型倍率 + 分组倍率），token 用量取自本项目
实测（`data/**/*_server_response*.json` 的 `usage`）。计费口径是 new-api 的标准公式：

```
quota = (文本 token + 输入图 token × image_ratio) × model_ratio
        + 输出 token × completion_ratio × model_ratio
USD   = quota × 分组倍率 / 500000
```

按次计费模型（`quota_type=1`，Gemini 图片与 `gpt-image-2-c`）：`USD = model_price × 分组倍率`。
**实测路由分组**（响应头 `X-Routing-Group`）：`gpt-image-2`（及文本通道）→ **Openai-Gpt-1（×0.88236）**；
`gemini-3-pro-image-preview` → **Discounted-Banana-1（×0.110295）**。

### 单张成本（1024×1536、挂 1 张画风参考图、提示词 ≈1,300 字符）

| 工序 | 单价 | 说明 |
|---|---|---|
| gpt-image-2 `low` | **$0.019** | 输出 token ≈343 |
| **gpt-image-2 `medium`（推荐）** | **$0.039** | 输出 token ≈1,105 |
| gpt-image-2 `high` | **$0.155** | 输出 token ≈5,500（实测分布） |
| gpt-image-2 `medium` 不挂参考图 | $0.031 | 少一张输入图 |
| 全图重绘 Gemini 3 Pro Image @2K | **$0.036** | 按次 $0.33 × 0.1103 |
| 局部重绘 + 羽化贴回（再一次 Gemini） | **$0.036** | 同上 |
| 结构线叠加 | **$0** | 纯本地 |
| 分析链路（Step1~5 + 两档字段 ≈7 次 `gpt-5.6-luna`） | **≈$0.016** | luna ratio 0.1 |

**全工序合计：约 $0.11 / 张（不含分析）、$0.13 / 张（含分析）≈ ¥0.92。** 用 `high` 出首图则 ≈$0.23/张。

### 提示词长度护栏（GUI 里实时显示，超线变色）

| 线 | 值 | 依据 |
|---|---|---|
| **软上限** | **2,000 字符** | 超过它「画风参考图」基本失效：画风相似度 0.323 → 0.107（§4.19） |
| **硬上限** | **15,000 字符** | 本中转站实测 15,662 字符的组合直接 `ConnectionResetError`（§4.16） |
| 官网上限 | 32,000 字符 | 官方文档 `maxLength`；别依赖，中转站先断 |

长度对**钱**几乎没影响：从 1,300 加到 11,000 字符，首图成本只从 $0.039 涨到 $0.053（+$0.014，约 +36%），
因为文本 token 只占极小头；**真正的代价是功能性的**——参考图失效 + 断连风险。所以先看长度护栏，再看成本。

GUI 的位置：gpt-image-2 Tab 的提示词框正下方常驻两行——
`提示词 N 字符 ｜ 建议 ≤2000（画风参考图才生效）｜ 硬上限 15000 ｜ 还能输入约 X 字符`
`单张全工序估算 ≈ $0.127（≈¥0.92）｜ 首图 $0.0389 + 全图重绘 $0.0364 + 结构线叠加 $0.0000 + 局部重绘 $0.0364`，
并按当前勾选框与画质实时重算；超软上限变橙、超硬上限变红。

## 五、参数速查

| 项 | 推荐 | 备注 |
|---|---|---|
| prompt 长度 | 画风短版 ≤680 + 内容锚 ≤500（挂参考图）/ ≤1400（不挂） | >2,500 字符：参考图失效；>15k：中转站断连 |
| `quality` | `medium` | `high` 细节更多但留白被吃、水彩感变差 |
| 尺寸 | `1024x1536`（2:3 竖图） | gpt-image-2 只有 3 档 |
| 输出格式 | PNG | JPEG 会污染细线端点与色块指标 |
| 重绘分辨率 | `2K` | `1K` 只适合预览，`4K` 会多"凭先验补细节" |
| 重绘比例 | `auto` | 固定比例会裁切/拉伸非该比例的源图 |
| 结构线强度 | 0.50 | 0.35 更保守 |
| 局部重绘羽化 | 40~64 px | 越大改动越局部、接缝越软 |
| 局部重绘放大 | 1.0（裁切区 ≤2048 时）| 放大到 >2048 会被接口压回来，等于先放大再缩，只会更糊 |

## 六、已知边界（别在这些地方浪费时间）

1. **线条连续性由参考图自身的边缘语言决定**，与参考图分辨率无关；软边画风（say-hana/noir）无论怎么改写文字都到不了 tid 的线条水平（§4.11）。
2. **水彩厚涂与"全部线条连续"存在原理上限**，合理目标是"主结构线连续、次级笔触保留断裂感"（Sol，§4.15）。
3. **Gemini 没有 mask**：局部重绘靠"裁切 → 重绘 → 羽化贴回"近似，无法做像素级锁定。
4. **高调/低饱和素材照容易过淡**：v5 的"不许再降饱和"条款能挡住，但 v4 + 线条段一起用会互相干扰（§4.14）。
5. **这张素材照类的内容（丝袜/抬腿）在 relay 上会间歇触发审核**，建议措辞净化 + 腰以上构图（§4.13）。

## 八、本轮补充（清晰度 / 画风抽查 / 流程状态）

### 1. 手、鞋细带为什么看着还糊 → 因为那批产物**没跑重绘**
W5 / W7 是「分析短锚 → gpt-image-2」的直出图，**没有经过 Gemini 重绘**（只有 W1 那组跑过）。同一张 W5 做对照（裁切归一到 520px 高再算）：

| 版本 | 手部(左) 段长/端点/锐度 | 手部(右) | 鞋部 |
|---|---|---|---|
| A gpt-image-2 直出 | 90 / 26.0 / 131 | 110 / 21.4 / 104 | 86 / 17.6 / 74 |
| **B 重绘 2K** | **133 / 22.2 / 165** | 125 / 18.7 / **148** | **134 / 16.3** / 52 |
| C 重绘 2K + 结构线 0.5 | 103 / 23.8 / **200** | **152 / 15.4 / 168** | 125 / **12.9** / 69 |
| D 重绘 4K + 结构线 0.5 | 104 / 20.8 / **246** | 121 / 20.0 / 185 | 101 / 17.9 / **83** |

**结论**：细件（手指、鞋带）变清楚主要靠**重绘**（鞋部段长 +56%、锐度 +50%）；结构线叠加再补一刀锐度，4K 最高但耗时约 2 倍。所以「出图后立即重绘优化」是必勾项，细件多就上 4K。

### 2. 画风抽查：哪些画风的头发天生更碎
统一内容锚（480 字符）+ 各画风 `prompt_gpt` + 参考图，头发带指标：

| 画风 | 头发段长↑ | 头发端点密度↓ | 结论 |
|---|---|---|---|
| ajicoma | 106.4 | 25.6 | 好（≈ tid 家族） |
| goto-p | 100.3 | 26.3 | 好 |
| dall-e-v3 | 79.8 | 36.6 | 中等 |
| say-hana-style | 71.9 | 43.4 | **碎** |
| fuzichoco | 63.8 | 34.3 | **碎** |
| waterink-style | 59.0 | 38.7 | **碎** |

对最碎的两支跑「头发区域局部重绘 + 羽化贴回」后端点密度下降、段长上升 → **这类画风建议把「局部重绘区域 = 头发」常开**。
另外发现：**只挂画风参考图时，参考图的场景/道具会被带进来**（waterink-style 的参考图是室内，文本写海边，产物被拉成室内）。
已在 `compose_style_prompt` 补 `STYLE_REF_SCENE_FROM_TEXT`：声明"场景/道具/构图只来自文字，参考图仅提供调色/光照/笔刷/渲染语法"。

### 3. 流程状态 / 失败重试 / 中间产物
| 反馈 | 改动 |
|---|---|
| 还没出图就显示完成，后台还在跑二次渲染 | 分析 Tab 生图线程结束后不再立即放行：只要 `_active_post_threads` 非空就保持按钮禁用并提示"⏳ 仍在执行：…"，全部跑完才打印 `✅ 全流程完成（生图 + 后处理）`；gpt-image-2 Tab 完成文案带工序数、过程中状态栏显示当前工序 |
| 步骤多，失败节点要能智能重启 | 每一步写进 `<产物目录>/pipeline-steps/pipeline-manifest.json`（步骤/状态/产物/错误）；`run_pipeline(..., resume=True)` **跳过已成功步骤、只重跑失败那一步**；Tab 新增「重试失败步骤」按钮，失败时状态栏提示"部分完成：N 个后处理步骤失败" |
| 中间产物应单独放 | 结构线叠加 / 局部重绘 / 重绘提线的中间产物统一落到 `<产物目录>/pipeline-steps/`，清单 JSON 同目录 |

CLI 行为一致：`tools/overlay_structure_lines.py`、`tools/local_repaint_composite.py` 仍是单步入口，
批量串联走 `utils/post_process.run_pipeline`。

## 九、产物落盘约定（2026-09-23 起，含多线程安全）

| 产物 | 位置 | 命名 |
|---|---|---|
| **最终成图** | **`data/<YYYYMMDD>/`（日期根目录）** | `<来源名>-<run-id>-final-<工序串>.png`，例如 `xxx-005910-c139b2-final-sline40.png`、`xxx-xxxx-final-rp+sline50+local-hair.png`；**`-final-` 是最终产物标记**（一眼区分中间的 sline 图），工序串说明经过了哪些处理，run-id 保证多线程/重复跑不重名 |
| 中间产物 | `data/<YYYYMMDD>/pipeline-steps/<run-id>/` | 结构线中间图、局部重绘裁切图 `*-crop.png`、局部重绘原图、`pipeline-manifest.json` |
| 首图（有后续工序时） | `data/<YYYYMMDD>/analysis-gpt-image/` | 中间产物，最终产物由流水线写回日期根目录 |
| 首图（**没有**勾任何工序时） | `data/<YYYYMMDD>/` | 此时首图就是最终产物 |
| 分析结果 JSON / prompts TXT | **原图同目录**（如 `data/<日期>/sucai/`） | 投稿 Server 按"图片同目录找同名 JSON"配对，挪走会让服务器找不到原图；不勾「保存到原图同目录」时落 `data/<日期>/` |

**为什么中间目录必须带 run-id**：以前所有运行共用一个 `pipeline-steps/`（甚至直接落在日期根目录），
多线程并行时同一个来源名会互相覆盖（历史事故：`img-sline50.png` 被别的任务盖掉）。
现在 `utils/post_process.new_run_id()` 给每次运行一个 `HHMMSS-xxxxxx`，
中间目录 = `pipeline-steps/<run-id>/`，最终文件名也带这个 id。

**裁切图不再进发布目录**：`local_repaint_composite(..., scratch_dir=...)` 把 `*-crop.png` 与局部重绘原图
都写在运行目录里，日期根目录只留最终成图（以前会出现"`...-crop.png` 和最终图并排，分不清哪个是产物"）。

### 手部畸形的来源与规避（重要）
01:14 那次 GUI 产物（`repaint_001404-…-local-subject_no_face.png`）手指畸形、头发发糊，原因已定位：

1. 那次的**首图是 medium**（`usage.output_tokens = 1105`，high 是 ~5500）——说明当时跑的是**改动前还在内存里的旧代码**（GUI 没重启）；
2. **局部重绘区域选了整身局部重绘**：整身（除脸）被裁切重画，举起的那只手正好是重绘重灾区，模型把它重画歪了；
3. 结构线叠加作用在已经被画歪的手上，又把错线强化成"畸形感"。

规避顺序：**先重启 GUI 拿新代码（high 首图 + 自适应缩放 + 固件正文 + PNG）** → 手部敏感的场景**别用整身局部重绘**，
只做「全图重绘」或把局部区域限定到头发/裙子 → 需要单独修手时再考虑「手部」区域（目前没有 hands 预设，可按需加）。

### 队列（分析队列）的状态以最终产物为准
以前分析一结束就把那条记录标成绿色「已完成」，可后面还在生图/跑工序 —— 现在：
1. 分析完成时，如果本任务还会自动生图 → 记录保持 `进行中·生图/后处理中`，**不标绿**；
2. 生图完成后如果还有后处理线程（JPG upscale / WebP 等）→ 继续 `进行中·后处理`；
3. 只有**所有线程都结束 + 确实拿到最终产物**（`final_products`，或 `data/<日期>/` 里带 `-final-` 的产物）才标绿；
4. 线程都结束但没产物 → 停在 `进行中·等待最终产物`，并在日志里告警，不假装完成。

回归用例：`test_queue_marks_success_only_with_final_product`、`test_queue_stays_running_while_post_process_running`、

- **小硬件可数性**：鞋眼/鞋带结/扣件达到"故事级可辨"，但达不到"可放大的产品级细节"；
  已用「条款 + 紧框 + 4K」压到当前模型能力上限。
- **中转站限流**：密集跑图后 `/images/edits` 会间歇 ConnectionReset（各种载荷大小逐项测试均成功，
  已确认不是载荷问题）；已加 `partial` 最终产物兜底，失败也能交付并可从失败步重试。

## 二十一、为什么 024958 那版看起来更清楚（线条"稀碎"的真正原因）

用户看好的产物 `…024958_0_afd8ee-…-final-rp+sline50+local-subject_no_face.png` 与后续版本的实测对比（900px 归一）：

| 样本 | 亮度 | 饱和 | 局部 RMS | 段长 | 端点 | **线-底对比** |
|---|---|---|---|---|---|---|
| **A 024958（无内容参考图）** | 136.6 | 79.0 | 39.9 | 75.9 | 35.9 | **−15.4**（线比底暗 15） |
| B R2T（有内容图，无色调） | 170.7 | 69.9 | 32.5 | 77.4 | 31.9 | **+4.6**（线比底还亮） |
| C R3（有内容图 + 旧色调） | 158.2 | 82.3 | 49.0 | 76.8 | 35.8 | **−0.5**（几乎无对比） |
| tinkle 参考图 | 135.6 | 113.3 | 36.1 | 98.6 | 20.4 | +12.3 |
| **② 新：色调目标=画风参考图** | **144.4** | **89.1** | 45.0 | 77.1 | 34.6 | **−16.7** |
| ① 新：色调目标=输入照片 | 154.4 | 75.9 | 43.3 | 81.6 | 33.2 | −11.2 |

**结论**：三版的**几何其实一样**（段长 75.9 / 77.4 / 76.8，端点 32~36），差别全在**明度关系**——
A 版的线条比底色暗 15 个亮度级，看起来就"清楚"；B/C 版线条与底色几乎同亮度（+4.6 / −0.5），
线条自然"糊/碎"。造成这个差别的是我后来加的**内容参考图**（照片是高明度浅色 → 整图被抬高到 170）与
**色调校准的目标取了照片亮度**（155）以及旧版的 S 曲线（压掉局部对比）。

**修法（已实现）**：
1. 色调校准默认**不打中对比**（`contrast 1.00`，S 曲线是压碎线条的元凶：段长 87→77）；
2. 新增 `--tone-target photo|style`，**默认 style（画风参考图）**：亮度 144.4 / 饱和 89.1 / 线-底对比 −16.7，
   比 A 版还清楚，且色调校准只动亮度与饱和度、不动色相，角色固有颜色关系不变。

## 二十二、画质优先预设（`--preset quality`）

用户决定「质量更高，牺牲一点色差」，据此把已验证的改法打包成预设：

```
--preset quality  ==  --content-ref on --repaint-ref style --extra-region shoes_zoom,waist,thigh
                      --tone --tone-target style        # 色调目标取画风参考图（更深、更饱和）
                      --ink --ink-target 8              # 线条加墨：只压线条像素，让线明显深于局部底色
```

同一张中间态的实测对比（900px 归一）：

| 方案 | 亮度 | 饱和 | 局部 RMS | 段长 | 端点 | **线-底对比** |
|---|---|---|---|---|---|---|
| A 用户看好的旧版（无内容图） | 136.6 | 79.0 | 39.9 | 75.9 | 35.9 | −15.4 |
| 未色调中间态 | 176.7 | 59.1 | 37.6 | 87.0 | 31.1 | +2.2 |
| 色调目标=照片（fidelity 路线） | 154.4 | 75.9 | 43.3 | 81.6 | 33.2 | −11.2 |

结论：`--preset quality` 的「线-底对比」比用户看好的旧版还清楚（−20.0 vs −15.4），

## 二十三、`--preset quality` 端到端跑通时抓到的两个真 bug（2026-09-23）

第一次 `--preset quality` 端到端（repaint → structure → local(4 区域) → tone → ink）在第 3 个局部区域
（waist）上失败，只交出 `…-final-partialrp+sline-…png`；顺着日志查下去抓到两个一直存在的真问题：

### ① 「鞋/靴紧框」其实没生效（`detect_footwear_box` 是死代码）

`shoes_zoom` 在 `DYNAMIC_REGIONS` 里，但 `resolve_region_box` 只判断"是不是动态区域"，
然后**一律返回 `detect_subject_box`** —— 专门为它写的 `detect_footwear_box`（主体遮罩里最靠下、
面积最大的连通块）从来没被调用过。后果：

- 鞋靴 FOCUS 条款（"this crop is a TIGHT close-up of ONE OR TWO shoes / 每个鞋眼是一个带暗孔的环…"）
  被贴在**整张全身裁切**上，提示词与画面自相矛盾 —— 这类矛盾正是"绑带/扣件乱画"的温床；
- 像素预算摊平到全身：实测同一张 1696×2528 的产物，两个区域产出的 `-local-*-crop.png`
  **逐字节相同**（MD5 都是 `54F7112875553AD5E445E6CCC9737BE0`），"细节最大"根本没发生。

**修法**：`resolve_region_box` 对 `shoes_zoom` 走 `detect_footwear_box`；裁切从 1592×1990（整个人物）
变成 1641×758（下缘 30% 的双脚紧框），同一个鞋区在输入里占的像素密度提高约 2.6 倍。
另外新增 `TIGHT_REGIONS`：紧框区域算"只贴回主体"的遮罩时**改用整个人物框**跑 GrabCut ——
拿贴边的紧框当 GrabCut 矩形先验，算法会判成"框内全是前景"、遮罩近乎全空，贴回等于没贴。

### ② `detect_subject_box` / `subject_mask` 每次调用结果都不一样（GrabCut 没设种子）

GrabCut 内部用 OpenCV 全局 RNG 初始化 GMM。同一张 1696×2528 的产物连调三次
`detect_subject_box`，得到 **(46,663,…) / (337,351,…) / (46,422,…)** 三个不同的人物框。
于是"同一条命令跑两次"裁到不同位置：局部重绘的裁切框、主体遮罩、鞋靴紧框全在漂移，
拼接/漏贴出现的位置既不能复现也不能比较（排查"下半截拼接错误"时这一点尤其致命）。

**修法**：`GRABCUT_SEED` + `_seeded_grabcut()`，`detect_subject_box` / `subject_mask` 统一走它；
连调三次得到同一个框（回归用例 `test_subject_box_is_deterministic`）。

### 验证

- 紧框重绘单独跑通（Gemini 4K，61.9s，裁切 1769×758 补边到 21:9）；
  鞋区新旧对比：改动像素占比 0.279（旧·全身框）→ 0.223（新·紧框），画面更干净、没有新增偏差。
- `--preset quality` 的**首图**两次都被中转站 `ConnectionResetError(10054)` 拒（不是载荷问题，
  见 §二十 已知边界）；改用已有中间态 `…-sline50.png` 续跑 local(4 区域)+tone+ink 全流程通过，
  交出**完整**（非 partial）最终产物：`data/20260923/repaint_224700-1cae00-sline50-225339-47bd72-final-local-subject_no_face+tone+ink.png`
  （亮度 140.9 / 饱和 88.5，与 §二十二 的目标 142.2 / 89.8 一致；肤色、蕾丝、袜带、鞋结都可读，
  没有拼接/重影/半截肢体）。
- 回归用例：`tests/test_post_process.py` 新增 3 条（确定性 / 紧框接线 / 紧框遮罩用人物框）。

> 符号约定：`post_process.line_contrast` 返回 `底色 − 线`，**正数 = 线比底深 = 清楚**；
> 本文档 §二十/§二十二 的表格用的是相反符号（`线 − 底色`，负 = 线更暗），所以
> 同一个 +14.7 在那两张表里写作 −14.7。

## 二十四、端到端策略：分析图 → 生图到底是"再画一张"还是"描图"（2026-09-23）

用户看到 `…_224603_0_6e73a5-…-final-partialrp+sline-…png` 与 `…_223134_0_4b1226-…` 两版产物后指出的问题：
**人物的姿势与输入图一模一样** —— 这跟「分析图再生产图」的目标不一致。

### 实际发生了什么（查日志确认，不是猜测）

- 那两版是 CLI 实测跑的，命令里带了 `--content-ref on`：首图请求是
  `模式=/images/edits（参考图 2 张）` —— **Image 1 = 分析用的原照片（6336×9504 压到 1365×2048）**、
  Image 2 = 画风参考图。挂了原图当"内容真值"，姿势/机位/构图自然被锁死，重绘再沿用这张图 → 出来就是原图那张画。
- 但**不挂原图也不够**：分析字段本身就忠实描述了输入图的姿势与构图，例如
  `gpt_image_prompt_short` = "One young woman **seated diagonally on the edge of a wooden chair**, torso tilted,
  left hand pinching her throat bow … **full-body vertical 2:3, slightly left of center**"。
  这段文字丢给模型，它照样会照着摆姿势。GUI（单图分析 Tab）从来没挂过原图，但出的图同样会像原图，原因就在这里。

### 定下来的策略（默认"再画一张"，描图是可选模式）

| 模式 | 触发方式 | 行为 |
|---|---|---|
| **新图（默认）** | CLI `--composition new`（默认）/ GUI「重新构图」勾选（默认勾上） | 只把分析**内容**（人物身份与配色、服装设计、道具、场景）当输入，提示词追加 `analysis_gen.RECOMPOSE_CLAUSE`：**换新姿势、新机位、新构图**，明确禁止复刻原图的姿势/机位/裁切 |
| **保姿势 / 沿用构图** | CLI `--composition keep`，或 GUI 取消勾选「重新构图」 | 不追加条款，模型会按描述原样摆姿势；适合"把这张图重画成另一种画风" |
| **描图** | CLI `--content-ref on`（或 GUI「首图直接用分析原图」） | 把分析原图当内容参考图挂上（`/images/edits` 两图），构图完全由原图决定；此时 `composition` 强制为 `keep`（图文冲突会让画面自相矛盾） |

- `--content-ref` 早先默认 `on`（当时为了压住画风参考图把发色/瞳色带偏的问题），现在**默认 `off`**；
  "角色固有特征被画风图带偏"这件事改由**文字条款**兜底（`CHARACTER-INTRINSIC FEATURES…` + `STYLE_REF_EXCLUSION`）。
- 只管首图：三道工序（重绘/结构线/局部重绘）都以**首图产物**为真值，与输入照片无关；
  重绘的第二张参考是画风图或线锚图（`--repaint-ref style|line|both|none`），不是原图。
- GUI 开关位置：单图分析 Tab → gpt-image 通道 → 「重新构图（不照搬分析原图的姿势/机位）」（常驻可见，默认勾选；
  勾了「首图直接用分析原图」时自动置灰，因为那条路线本来就沿用构图）。

### 与"保真"的取舍（如实记录）

不挂原图 + 重新构图，代价是**角色的固有特征（发色/瞳色/肤色）只能靠文字锚**，实测不如挂原图稳
（迁移测试 T3 曾出现玫瑰粉发 → 银白）。所以要"画得像那个人"时仍可以开 `--content-ref on`；
但那是描图模式，跟"分析图再生产图"不是一个目标，别拿它当默认。

### 实测 A/B（同一分析产物、同一 tinkle 画风、`quality=medium` 首图）

| 版本 | 参考图 | 内容锚 | 结果 |
|---|---|---|---|
| **新构图 + 短锚** | 1 张（只有画风图） | `gpt_image_prompt_short` 480 字符 | 姿势/机位确实换了（换椅子、换朝向、换腿姿），**但栗色长发被画成银白** —— 短锚里根本没写发色瞳色 |
| **新构图 + 完整档**（改后默认） | 1 张（只有画风图） | `gpt_image_prompt` 1271 字符 | 姿势/机位同样换了（另一套坐姿与腿姿），**栗棕长发 + 青色眼睛保住了**，服装/道具/场景一致 |
| 描图（`--content-ref on`） | 2 张（原照片 + 画风图） | 短锚 480 字符 | 构图与输入图基本一致（原姿势、原机位、原腿部排布）—— 这就是用户看到"一模一样"的那条路线 |

**由此定下的一条规则**：`composition="new"` 且**不挂内容参考图**时，内容锚自动从短锚（≤500）
升级到完整档（≤1400）——短锚是为"挂内容图、让画风图更容易起作用"设计的，里面往往只有姿势+服装；
一旦没有图，它就必须承担人物身份，缺了发色/瞳色就会换人。
（提示词总长 6271 字符，仍在硬上限内；见 `analysis_gen.build_gpt_image_request` 的 `content_tier`。）

## 二十五、手部错位：根因在首图，不在局部重绘（2026-09-23 排查）

用户指出 `repaint_230018-…-final-local-…+tone+ink.png` 与 `…-tone-…-final-ink.png` 两版**手部错位**，
并问为什么不能像 `…_output_023401_0_df78d4-023401-8d7d0f-final-rp+sline50+local-subject_no_face.png` 那样生成。

### 逐阶段定位（同一张产物，按像素 diff）

| 阶段 | 改动像素占比（>12 灰阶） | 结论 |
|---|---|---|
| `local`（4 区域贴回） | **1.0%** | 局部重绘几乎没碰画面 —— 它既没修手，也没弄坏手 |
| `tone`（色调校准） | 81.0% | 全局明度/饱和度 |
| `ink`（线条加墨） | 10.4% | 只压线像素 |

所以错位是**首图/重绘阶段**就有的：那两版走的是 `--content-ref on`（描图），模型必须复刻照片里
"手捏喉结蝴蝶结"的姿势，画崩了；而用户看着好的 `023401` 那版是**不挂内容参考图**的路线
（画面里是另一个角色、另一套构图与姿势）—— 正是 §二十四 现在的新默认。**姿势与手都由模型重画，
比让它照着一张照片复刻手要稳得多。**

### 试过又撤掉的方案：自动「手部紧框」区域

思路是 `detect_hand_boxes`（YOLO pose）→ 每只手 4K 重绘 + 手部条款。实测**必须撤掉**：

1. 姿态模型是给人像照片训练的，在厚涂插画上给的手腕位置离谱：两个"手"框一个落在**袖子**上、
   一个落在**胸衣蕾丝**上（`-crop.png` 里根本没有手）；
2. 模型照着"修手"条款执行，**在蕾丝上画出了几根裸手手指**（产物里出现一块补丁状的裸手），
   比原来的错位更糟；
3. 顺带发现整图 GrabCut 在这种亮蕾丝背景上会估歪：`detect_subject_box` 只框住下半身（y 从 1293 起），
   于是"只贴回主体"的遮罩把上半身的区域整块切掉 —— 表现是 QA 报 **改动像素占比 0.000**，白跑一次 API。

保留的改进：遮罩在**本次区域**内覆盖 < 2% 时不再用它（`local_repaint_composite` 里改为整框贴回并打日志），
避免静默地"什么都没做"。回归用例 `test_region_mask_falls_back_when_it_covers_nothing`。

### 结论 / 现在该怎么做

- **手部画坏的根本解法在首图**：用默认的「新图（重新构图）」模式，不要用描图模式；手由模型自己画。
- 要修手请**手动给坐标区域**（自动检测在插画上不可信）：
  `python tools/local_repaint_composite.py --image <图> --crop <x0,y0,x1,y1> --firmware prompts/gpt-image-optimize/repaint-system-conservative-v5.md --out <图>`
- 别再顺手加回"自动手部区域"：这一段是踩过坑的记录（`utils/post_process.py` 的 `REGION_EXCLUSIONS` 上方也留了注释）。

## 二十六、按用户要求重构 gpt 通道工序（2026-09-24）

用户对「分析图→生图」提出了明确的五条要求，已实现（本节是当前权威描述，前面 §二十四 的构图开关已废弃）：

1. **提示词 = 画风 `prompt_gpt`（最前）+ 与 Gemini 通道同源的分析描述**。
   内容不再用 gpt 专用短锚字段（`gpt_image_prompt_short/_full`），改用分析产物里那段描述素材
   **特征、构图、服装、道具**的文本（`prompt_context` 的 original/refined 描述，缺了退回分析 JSON 的
   `english_description`）。GUI 里**删掉了「重新构图」勾选框**，`analysis_gen.RECOMPOSE_CLAUSE` /
   `composition` / `content_tier` 一并删除（`build_gpt_image_request(..., content_text=...)`）。
2. **首图走「新建图片」而不是 edits**：`generate_image_aigc2d_gpt(mode="generate")` →
   `POST /v1/images/generations`，画风参考图放进 JSON 的 `image` 字段（base64 data URI，实测中转站接受）。
   这样模型是"按文字新建一张图"，不会像 `/images/edits` 那样把参考图当原图去编辑。
3. **尺寸跟随输入图比例**（`gpt_size_follow_cb` 保持默认勾选）。
4. **局部重绘统一 2K**：`pipeline_steps_from_flags(detail_boost=False)`，
   不再把 face/hair/shoes/waist/thigh 自动升到 4K。
5. **超时按「一道工序一份」**：`single_analyzer` 里 `timeout_budget = 每道工序秒数 × (首图 1 + 工序数)`，
   不再用 120 秒掐掉整条链（high 画质首图 + 三道工序必然超过 120 秒）。

> **重绘的第二张参考 = 画风参考图（2026-09-24 修复）**：GUI 以前没给 `run_pipeline` 传
> `style_ref_path`，于是 `reference_mode` 落到默认的 `line_anchor` —— 自动生成的线锚图
> （白底长结构线）被模型当成"渲染语言"，实测要么把整张图塌成白底线稿（矩阵 6 次里 4 次），
> 要么把线网印成**"碎玻璃"纹理铺满人物**（用户："给参考图加个玻璃是完全错误的"）。

### ④ 线条加墨改成「迭代到目标」，同一套预设的线条清晰度才稳定

同一条 `--preset quality`、同一张分析图，两次跑出来的「线-底对比」差了一个数量级：

不够就再压一遍（`max_passes=4`），单像素累计压深不超过 `max_darken`（默认 40）。

已经达标的产物再跑一遍原样返回（幂等，不会越跑越黑）。回归用例：
`test_ink_lines_iterates_until_target_within_budget` / `test_ink_lines_noop_when_already_dark_enough`。

> 靠后处理加墨只能补到目标线（+8），补不出 A 版那种 −15 的清爽感 —— 想让画面更"清楚"，

### ③ 顺手修掉的中转站坑：`Unknown parameter: 'image'`

批量过程中 `puracotte-style` / `say-hana-v5` 的首图连续失败，原始返回：

```json
{"error":{"message":"Unknown parameter: 'image'.","type":"invalid_request_error","param":"image"}}
```

原因是中转站**按请求随机挑上游通道**，其中一部分不认 `POST /v1/images/generations` 的 `image` 字段
（同一份请求换个通道就正常，实测同一批次 3 成功 2 失败）。修法（`modules/others/api_backend.generate_image_aigc2d_gpt`）：

1. 「上游返回错误 + 空 data」时**重发**（`upstream_error_retries`，默认 2 次，间隔 `retry_backoff`）；
2. 重发仍失败且报错里含 `image` → **回退 `/images/edits`（multipart）再发一次**，并在日志里写明
   「已回退到编辑端点重发」，因为 edits 的语义更接近「把参考图当原图编辑」，产物可能有差异，需要能追溯到。

## 三十、**四区链会把画面拼坏**（2026-09-24 用户复核后的诊断，重要）

用户看 5 画风批量结果时指出「fuzichoco 和 tid 两组都完全跑挂了，感觉最后的拼合阶段引入了太多问题」。
逐环节差分 + 免费对照实验后，**结论成立**：坏的不是 `repaint` / `sline50` / `tone` / `ink`，而是
**局部重绘（四区链）的「裁切 → 重绘 → 贴回」**。完整证据页：`DIAG-local-chain.html`。

### 机制

Gemini 对**裁切图**会**重新构图**（在裁切内部移动/缩放主体、改变取景），贴回原坐标时内容对不上 ——
表现为一块带硬边界的错位内容块（tid 是腿/丝袜区的黄绿块，fuzichoco 是裙摆/大腿的青绿块）。

### 证据（`log/diag-local-chain.txt`，逐步差分，阈值 18 级）

「变化像素占比 / 最大连通块面积占比 [+ 块内平均色差 B/G/R]」：

| 画风 | +subject_no_face | +shoes | +waist | **+thigh** |
|---|---|---|---|---|
| tid | 6.4% / 0.8% | 7.0% / 1.5% | 2.6% / 1.0% | **9.1% / 7.6%，+6.6/+11.9/+4.4** |
| fuzichoco | 6.7% / 2.2% | 8.0% / 2.4%，−13.5/+15.4/+25.5 | 3.8% / 2.0%，+13.7/−25.0/−45.6 | **16.4% / 15.9%，−33.1/−18.1/−27.9** |
| shiratamaco | 4.9% / 0.9% | 6.7% / 1.5% | 3.9% / 1.1% | 2.6% / 0.4%（干净） |
| puracotte | 3.0% / 1.5% | 3.8% / 1.5% | 2.9% / 1.3% | 3.1% / 1.6%（干净） |
| say-hana-v5 | **10.5% / 9.0%** | 10.8% / 9.3% | 3.5% / 1.3% | 6.3% / 2.9% |

- **`thigh` 是重灾区**（两族一步换掉 7.6% / 15.9% 的画面），`waist` 在 fuzichoco 上也有一块；
- `sline50` 阶段两张图都是干净的（差分与肉眼都确认）；
- 免费对照（用已有 patch 重做贴回，零 API）：默认 / `restrict_to_subject=True` / 羽化 16 / 羽化 96
  **四种都有同样清晰的矩形错位边界** → **是几何错位，不是融合/遮罩/羽化问题**；
- 命中率：5 画风 × 4 区域 = 20 次局部调用里，明显拼坏 3 块（tid-thigh、fuzichoco-thigh+waist）、
  另有 say-hana 的 subject_no_face 一步换掉 9.0%；**本轮 5 张终图报废 2 张**。

### 修法（按性价比，未实施，待用户决定）

1. **贴回前加「几何一致性闸门」（推荐，零 API 成本）**：把 patch 与 crop 的梯度图做归一化互相关 /
   比较主体包围盒与质心；位移或尺度偏差超阈值 → **丢弃该 patch**（保留 sline50 的版本）并记日志。
   最坏结果只是「少了一次局部修补」，不会污染画面。
2. **默认不要贴大块身体区**：`subject_no_face`(1526×2479) / `thigh`(1272×860) / `waist`(1085×708)
   这类大裁切最容易触发重新构图，`shoes`(1696×506 的条带) 相对安全 → 默认改成「不勾局部」或「只勾 shoes」。
3. **换个做法**：不裁切，直接把**整幅图** + 「只重画 thigh 区」的强调句交给模型（即 `repaint` 的模式，
   几何天然对齐），代价是分辨率摊薄。
4. **给局部调用带第二张参考（整幅缩略图）**，让模型知道裁切在整幅里的位置（需实测）。
5. **对齐后再贴**（估计 dx/dy/scale）—— 只能治轻微平移，对「重新构图」无效，备选。

> ⚠️ 因此 **「重绘 → sline50 → 四区 → 色调 + 加墨」这个配方里，`sline50` 之前的部分与 `tone/ink` 都成立，
> 唯独 `四区` 不能用默认值**。GUI 默认（`ANALYSIS_GPT_UI_DEFAULTS` 里的四区链）在用户确认前**不要当成已验证配方**。
