# gpt-image 系列上的「画风生图」可行性实验（tid 画风，2026-09-20）

> **要用法先看两份操作文档**：`BEST-PIPELINE.md`（当前最优解 + 完整工作流，逐道工序的勾选框与实测收益）
> 与 `BEST-PROMPT.md`（首图提示词模板）。本 README 是全部实验数据与结论。
> 目录里的实验按时间排：`overnight-20260920-21.html`（12 批次 / 161 图全景）、`round-20260921.html`（本轮画廊）。

本项目在 Gemini（`gemini-3-pro-image-preview`）通道上已经把「画风生图」玩得很顺：几千词的画风指令 + 一张画风参考图 + 参考优先 / 图文交错等四种模式，出图很稳。
同样的输入换到 gpt-image-2 通道就被质疑「表现很差甚至无法生图，可能是前置引导词太长，gpt-image 不支持那么长的输入」。

这份记录是针对性复核：**gpt-image-2 / 2.5 到底能吞多长的提示词、长提示词会不会毁掉画风、参考图在多大程度上真的在起作用**。
结论先放这里：

1. **长度不是硬门槛**。官方文档写得很清楚：`/images/edits` 与 `/images/generations` 的 `prompt` 都是 `maxLength 32000`（字符）。实测把 **31000 字符和 40000 字符**的提示词直接发过去，上游照样出图（40000 已超文档上限，也没被拒，属于「不要依赖」的灰区）。
2. **「无法生图」另有原因**，八成不是长度。本轮 22 + 12 + 8 次请求 0 失败；真正常见的失败源见文末「失败排查」。
3. **长提示词的真实代价是「参考图失效」**：11k 全量指令会赢走风格主导权（真实提示词验证里配色贴合度 0.119 vs 短说明 0.390）；「少女站在浅水」这种稀疏主体还会被画成水下精灵。准确说法不是「长文本必崩」，而是**长文本会把参考图挤掉，主体崩不崩取决于它自己描述够不够硬**。
4. **参考图在这个通道里非常强，但用不好会连主体一起搬**：会连**参考图角色的发色/瞳色一起复制**（粉发 + 金瞳就是 tid.png 本人的特征）。要么用「角色分工声明」，要么改用**结构化风格字段**（§4.6，实测最优）。
5. **`quality` 别默认 `high`**：同 prompt 下 `high` 会把白底占比从 0.439 压到 0.222、边缘密度从 0.0722 提到 0.0934——细节变多、留白变少，水彩感反而变差。默认 `medium`。
6. `gpt-image-2.5-flare / -sunburst` 用同样的短说明反而表现更好，且输出 token 只有 gpt-image-2 的约 1/3。
7. **当前最优解已按 §4.6 更新**：结构化风格字段（Palette/Lighting/Brushwork/Edges/Texture/Composition density/Detail level/Avoid，~250 字）+ 参考图，实测 HSV 0.644、亮度 238.8、饱和 13.3、白底 0.686、边缘密度 0.0364（参考图 221.5 / 25.0 / 0.667 / 0.0663），且不复制参考图角色特征。模板见 `BEST-PROMPT.md`。
8. **已落地到项目**（§4.7）：`config-styles.json` 每个画风新增 `prompt_gpt` 字段（8 字段短版），生图链路按 `api_type` 自动切换；转换规则见 `prompt-gpt-rules.md`，批量转换见 `tools/convert_styles_gpt.py`，参考图客观统计见 `tools/style_ref_stats.py`。

> 本轮全部产物、提示词原文、指标原始表与文档快照都在本目录下，可直接复查（目录清单见 §7）。
> **只想拿用法**：直接看 `BEST-PROMPT.md`（可直接粘贴的最优解模板 + 参数）；想把画风说明改造成 gpt-image 版看 `prompt-gpt-rules.md`；想搞清原理看本文全文。

## 1. 官方文档怎么说（要点摘录）

抓取方式：本机 `curl`/`.NET` 出网被墙，统一用 python 走**本机 HTTP 代理**（端口见 `PROJECT_REQUIREMENTS.md`，不入代码常量），脚本见 `tools/`（仓库外的一次性脚本已清理，抓回的正文快照放在 `web/`）。

### 1.1 接口硬约束

| 项 | 约束 | 来源 |
|---|---|---|
| `prompt`（`/images/edits`） | `minLength 1` / **`maxLength 32000`**（字符） | [Create image edit](https://developers.openai.com/api/reference/resources/images/methods/edit) |
| `prompt`（`/images/generations`） | 同为字符串型描述字段 | [Create image](https://developers.openai.com/api/reference/resources/images/methods/generate) |
| 参考图张数 | GPT image 系列**最多 16 张** per request | 同上（`images` 数组） |
| 单图体积 | `image_url` 的 `maxLength 20971520`（20 MB，base64 data URL 长度上限） | 同上 |
| `size` | `auto` / `1024x1024` / `1536x1024` / `1024x1536`；2.5 的 `flare` 之类支持任意 `WIDTHxHEIGHT`（两边都要 16 的倍数，长短边比 ≤3:1，总像素 655,360~8,294,400） | 同上 + [Image generation guide](https://developers.openai.com/api/docs/guides/image-generation) |
| `input_fidelity` | **gpt-image-2 必须省略该参数**，API 不允许改——模型对**每一个输入图都按高保真处理** | 同上 |
| `quality` | `low` / `medium` / `high`（2.5 另支持 `xhigh` / `max`） | [Create image edit](https://developers.openai.com/api/reference/resources/images/methods/edit) |
| `usage` | 返回 `input_tokens_details{image_tokens,text_tokens}` 与 `output_tokens`，可用来精确核对「提示词有没有被截断」 | 同上 |

`input_fidelity` 那条是本次实验的**理论钥匙**：既然 gpt-image-2 对所有输入图都按最高保真处理，而 `/images/edits` 的语义就是「**编辑**这些输入图」，那么提示词越长、越抽象，模型就越会退回到「把这些图改一改」的行为模式——要么照抄参考图主体，要么按自己的老套路画。

### 1.2 官方提示词指南的口径

[GPT Image Generation Models Prompting Guide](https://developers.openai.com/cookbook/examples/multimodal/image-gen-models-prompting-guide)（Cookbook）明说了几件事：

- 「Rich, detailed prompts are the norm... **small wording/layout tweaks usually improve legibility**」——官方鼓励详细，但
- 「**Iterate instead of overloading**: Long prompts can work well, but debugging is easier when you start with a clean base prompt and refine」——**长提示词能跑，但不是推荐起手式**。
- 结构建议：`background/scene → subject → key details → constraints`，**复杂需求用短标签分段/换行，不要一整段长散文**（「use short labeled segments or line breaks instead of one long paragraph」）。
- 多图输入：**按索引和描述逐个引用**（「Image 1: product photo, Image 2: style reference」），并说明如何交互（「apply Image 2's style to Image 1」）。
- 5.1 Style Transfer 的官方范例短得离谱：`Use the same style from the input image and generate a man riding a motorcycle on a white background.` —— 一句就够。

也就是说：**官方推荐的做法是「短句 + 参考图」，不是「几千词说明书 + 参考图」**。本项目的 tid 全量指令（11,186 字符 / 1,417 词）正好反向。

### 1.3 社区/第三方实测：Image API 传参考图时提示词会被忽略

- 日文实测笔记 [「GPT Image 2」Image API 経由でリファレンス画像を渡したら、3 回連続でプロンプトが無視された](https://note.com/more_sunset/n/n8128a703259e)（2026-04-30）：同一张参考图 + 同一条英文提示词，`Image API` 连出 3 张都把**文案和「不要加 logo」这类禁止项一起无视**；换 `Responses API` 同条件一次通过。作者的归因是两者职责不同，并算了一笔账：Image API medium 单张 $0.055、Responses API medium 单张 $0.09（约 1.6 倍），但「连出 3 张废图」的话总成本反而 Responses API 更低。
- 这说明「参考图 + 提示词」在 gpt-image 的 Image API 路径上**服从性本来就弱**，与本轮量化结果一致（见 §5 观察 2、3）。

## 2. 实验设计

- 站点/通道：`new.aigc2d`（`apis.aigc-2d-gpt`）→ `POST /v1/images/edits`（带参考图）/ `POST /v1/images/generations`（不带）
- 模型：`gpt-image-2`（主）；`gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`（对照）
- 尺寸/画质：`1024x1536`、`quality=medium`（token 边界测试用 `1024x1024`/`low`）
- 画风：`conf/config-styles.json` 的 `tid`（`prompt` 11,186 字符 / `prompt_compressed` 1,758 字符 / `ref_image = data/style-ref/tid.png`，1000x1442）
- 统一主体（英文常量，所有变体一致，只变画风注入方式）：
  `A girl stands in shallow water at dusk, waist-up, looking at the camera, wearing a white dress.`
- 每次请求一张、顺序执行，产物落 `data/<日期>/gpt-image-tid/`，`*_server_response_*.json` 保留原始返回（含 `usage`）。

## 4.8 用户反馈的两个真问题 + `gpt-5.6-sol` 的诊断与修正（2026-09-21 晚）

用户指出 §4.6 的最优解 R5 有两个问题（都对着图看出来的）：

1. **画面过白、看不清**——主体与背景糊在一起；
2. **线条/发丝不连贯**（"像 SDXL 那样糊"）——这是最核心的问题。

把「参考原画 tid.png + R5 产物」一起发给 `gpt-5.6-sol`（视觉可读），它的诊断（原文 `sol-cases/answer_case_gpt-5.6-sol.md`）：

> **参考原画并不是以"透明水彩晕染"为主**，它更接近「清晰数字动漫线稿 + 平涂/柔和赛璐璐塑形 + 局部半透明水彩 + 少量纸面颗粒」。

也就是说我写的 `Brushwork: transparent watercolor-like washes with delicate fine lineart` 把**本该承担结构的头发/五官/服装也一起水彩化了**；再叠加 `Palette: lots of clean white` + `Lighting: bright high-key, soft even light` + `Avoid: heavy shading`，就同时制造了"过白"和"糊线"。

### 它给的修正（逐条）

| 原写法（问题） | 改成 | 为什么 |
|---|---|---|
| `lots of clean white` | `white-dominant background` + `controlled value separation` + `protected midtones` | 白色限定给背景，不再把整幅图推向纯白 |
| `soft even light` | `soft cool shadows at form turns, roots, folds and overlaps` | "均匀光"会消掉体积与遮挡阴影 |
| `Avoid: heavy shading` | 禁止的是 `clipped highlights / white-on-white loss of silhouette`，而不是所有阴影 | 明度锚点是骨架，不能一起禁掉 |
| `delicate fine lineart` | `continuous, confident linework, a small number of intentional lines` | "delicate/fine" 得到的是"很细很淡很多很碎"的线 |
| 水彩作为全局 Brushwork | 水彩只允许出现在 `distant clouds / water reflections / decorative accents` | 结构件（脸/发/眼/衣）不能用晕染法建模 |
| `Edges: soft, occasionally lost` | 明确列出必须 crisp 的部位（脸/眼/发轮廓/主发束/领口/裙缝/水线），lost edges 只留给远景 | 否则脸和衣领一起丢边 |
| （缺发丝描述） | 新增 hair 结构段：大块 → 中束 → 少量游丝；每束从发旋/发根出发、沿头颅曲率**连通到发梢**、有明确尖端 | 这是"发丝连贯"唯一可执行的写法 |
| （缺细节预算） | 三尺度细节预算：大轮廓 / 中景（发束·五官·衣褶·水线）/ 稀疏微料；微料只给脸与上身 | 细节在多个尺度上"争预算"是糊线的根因 |

### 实测（`sol-cases/`，同一主体「少女站浅水」+ tid 参考图）

| 版本 | 文本 | 亮度 | 中灰带占比 | 高光裁切>250 | 局部 RMS 对比 | 细尺度边缘占比 | 干净留白占比 |
|---|---|---|---|---|---|---|---|
| 参考原画 | — | 221.5 | 0.152 | 0.435¹ | 34.6 | 0.478 | 0.525 |
| **R5（旧最优）** | 628 | 238.8 | **0.041** | 0.312 | **12.4** | **0.778** | 0.602 |
| S1（Sol 完整版 + high） | 3574 | 199.7 | 0.480 | 0.037 | 28.1 | 0.639 | 0.175 |
| S3（Sol 精简版 + medium） | 2875 | 216.6 | 0.237 | 0.074 | 23.2 | 0.621 | 0.225 |
| V5-A（Sol 最终版 ≤2000 字符） | 2000 | — | 0.265 | 0.036 | 19.8 | 0.587 | 0.104 |

¹ 参考图的高裁切率来自它本身就是大面积白底插画，属于画风特征，不是缺陷。

**两个问题都解决了**：中灰带占比从 0.041 提到 0.24~0.48（明度层次回来了），高光裁切从 0.31 降到 0.024~0.074（不再曝光封顶），细尺度边缘占比从 0.778 降到 0.59~0.64（不再满屏碎线）。V5 是 Sol 压缩到 ≤2000 字符后的版本，跨 3 个主体（浅水 / 舞蹈 / 和服）都保持了同样的结构质量。

### 一个重要的方法论修正

Sol 同时指出**我们之前用的指标不该当目标**：

> 全局亮度和白底比例高度受构图影响；边缘密度不区分有效轮廓与噪声；固定阈值对色调映射敏感。参考图与生成图内容不同时，直接比较全图分布**主要测到的是构图差异，不是画风差异**。

它建议换成：分区亮度层次（人物/脸/头发/服装分别看 P10/P50/P90 与局部对比）、主体-背景分离度（轮廓两侧 ΔL*+ΔE00）、多尺度边缘比例匹配、线稿连通性（骨架化后看平均段长/碎线比例/端点密度）、负空间连通域、分区感知风格距离。

我已经把**可本地自动计算的前四项**实现了：`tests/style_render_metrics.py`（亮度分位/局部 RMS/中灰带/裁切率 + 三尺度边缘占比 + 骨架连通段统计 + 干净留白连通域，并给出 `render_score`）。按新口径重排：

| 产物 | render_score ↑ | tone | edge | line | space |
|---|---|---|---|---|---|
| V5-C（和服） | **0.534** | 0.485 | 0.848 | 0.602 | 0.019 |
| S1（Sol 完整版 high） | **0.513** | 0.502 | 0.595 | 0.572 | 0.319 |
| S3（Sol 精简版 medium） | 0.508 | 0.498 | 0.647 | 0.547 | 0.247 |
| V5-A（浅水） | 0.497 | 0.424 | 0.737 | 0.611 | 0.091 |
| **R5（旧最优）** | **0.486** | **0.398** | **0.349** | 0.621 | **0.713** |
| V5-B（舞蹈） | 0.436 | 0.338 | 0.688 | 0.542 | 0.070 |

结论：旧口径（亮度/白底/边缘密度）把 R5 排第一，新口径把 R5 排到倒数第二——**新口径与人的观感一致**。另外注意 `line_avg_len` / `line_long_ratio`：R5（78.1 / 0.756）其实并不比修正版（104~122 / 0.83~0.88）差太多，说明**它的问题主要是"线被高曝光与细碎边缘吃掉了可见度"，而不是线本身断开**——这解释了用户"像 SDXL 糊"的观感。

- 固件的完整性清单里有 `the hammock or any other support`（吊床）、`branch, moss, foliage and far shore` 这类**来自其它批次的具体物件**，对我们的主体是纯噪声；每次请求都带着 6k 字符，其中一大半是无关的清单项。
- 输出固定 JPEG：对线稿锐度有损（评估边缘密度/碎线时也会被压缩伪影干扰）。

### 于是做了一个「画风中性固件」并实测

`prompts/gpt-image-optimize/` 的 cel-shading 段落换成 **STYLE FIDELITY 段**：
先判定输入自身的渲染语言（水彩就还是水彩、平涂就还是平涂），**禁止跨媒介转换**，只要求"在既有画法内把线连起来、把形状读清、去掉色溢/带状"，
并且明确 `never flatten a painterly or watercolour look into hard cel shading`、线不许加粗。

实测（见上表 `中性固件` 两行）：**保真度大幅回升**（say-hana 配色相似 0.711→0.972、饱和度 86.5→101.4；tid 0.952→0.940 基本持平），

**建议**：
- 目标就是"干净线稿 + 平涂"的图 → 用**默认固件**（它在这类画风上最强）；
- 水彩/厚涂/柔和画风 → 用**画风中性固件**（`tmp` 实验版已固化为可选项，见 `prompts/gpt-image-optimize/`）；

产物：`data/20260921/tid-sol-v6-repaint/`（cel 固件）、`data/20260921/tid-sol-v6-repaint-neutral/`（中性固件）；归档副本 + 两份固件全文在 `repaint-cases/`；画廊 ⑧⑨ 段可直接对比。

### 再问 Sol 的复核结论（原文 `sol-cases/answer_repaint_gpt-5.6-sol.md`）

1. **默认固件确实改写了画风**：不只是修缺陷，而是"重新解释成标准硬边赛璐璐"——线被加粗成近似等线宽、颜色被归并成更少色阶（头发内部渐变、皮肤暖冷、白裙环境色偏都被压平）、柔和渐变被换成块状硬边阴影、纸感/空气透视变塑料化。**所以"平均段长 140→266"有一部分来自"线被加粗合并"，不能全算成修复**。
2. **中性固件保住了画风**（保留了细浅轮廓、柔和渐变、白裙的粉紫蓝灰变化），但仍丢了一部分微颗粒/细碎笔触/局部透明感，面部也被"标准美型化"（眼睛、脸型、嘴并非严格保真）。
3. **它指出一个我没注意到的违规**：重绘后**看起来很可能是重新取景/人物放大了**——这一点我用自动前景检测去验证过，但对该类画面不可靠（Otsu 前景会把天空/水面当主体），所以我暂时只作为**待人工确认的观察**记在这里：请你对着画廊 ⑧⑨ 与 ⑦ 段肉眼比一下构图是否被放大；如果确认，那 `aspect_ratio=auto` + "不要裁切"的文字约束不足以锁住取景，需要额外的构图相似度检查。
4. **手部只算中等改善**：Gemini 是"合理化重生成"而不是局部几何求解；被水面遮挡的手指、交叠发丝与肩带、发饰链条、小褶边这些，它修不稳。图 7（cel 版）的硬描边反而把不准确的手指结构强调了出来。
5. **固件定稿建议（c）两套可选、默认中性**：只有输入明确是硬边赛璐璐、或用户明确要求 cel 时才追加 cel 覆盖段；不要只留一套。它还指出**即使是 cel 模式也不该写死 `bold even-weight outlines` 和 `one hard-edged shadow tone per material`**——那两句话会把"细线 cel / 多阶 cel / 无外轮廓 cel"也统一成同一种风格。它给的中性版全文比我写的更保守（明确 `FIRST input image` 为基准、锁 `exact framing / crop / camera distance / facial identity / saturation`、禁止 `beautify / simplify`、修线仅限 `intended continuation is unambiguous`、不确定就少改），已存为 `repaint-cases/repaint-system-style-neutral.md` 的候选升级。
6. **参数**：`1K` 只适合预览；**`2K` 作为默认**；`4K` 不要当常规（生成式 4K ≠ 忠实修复，会产生伪细节与重设计），要放大就"先 2K 修复→检查→再独立 4K 放大"。**输出应该改 PNG**：JPEG 会在浅色渐变、水彩颗粒、高反差边缘产生振铃/色块，而我们要修的"色溢、带状、边缘杂质"有一部分正是被 JPEG 重新引入的。`aspect_ratio=auto` 不适合"严格保构图"任务，应该从输入图读比例并下发最接近值（本组竖图 = `2:3`）。**不要把参考原画无条件作为第二张图喂进去**：Gemini 会借用其人物/服装/背景语义（本轮参考图是校服+水池，很可能把语义带进海边白裙图），更稳的是先从参考原画提取结构化风格描述再用文字。
7. **瓶颈一句话**：**"Gemini 重绘环"——它能显著清线、提高完成度，但仍把"局部保真修复"当成整图再生成，导致画风、身份细节和取景发生不可控漂移。**

## 4.11 问题 1：为什么「线条连续」只在 tid 参考图下成立（`data/20260921/line-continuity/`）

用户观察到：同一套 v6 提示词，tid 参考图的产物线条明显连续（`v6-v6m`），而 say-hana / noir 的产物（`v6x-*`）没有改善。做了控制变量（同主体、同提示词，只换参考图）：

| 参考图 | 参考图宽 | 平均骨架段长↑ | 端点密度↓ | 长线占比↑ |
|---|---|---|---|---|
| tid 原图 | 1000 | **141.5** | **18.12** | **0.898** |
| say-hana 原图 | 832 | 99.8 | 25.33 | 0.837 |
| say-hana **放大到 1000px** | 1000 | **84.3** | **28.30** | 0.790 |
| noir 原图 | 816 | 98.1 | 25.47 | 0.822 |
| noir **放大到 1000px** | 1000 | 101.1 | 25.84 | 0.843 |
| **不给参考图（纯文本）** | — | 123.6 | 18.74 | 0.887 |
| ajicoma 原图（1664px，线条清晰的浅色厚涂） | 1664 | 127.7 | 18.84 | 0.876 |

**结论：决定线条连续性的是「参考图自身的边缘语言」，不是分辨率/像素量。** 证据：① 把 say-hana 放大到与 tid 同宽，指标反而更差（84.3/28.3）；② 完全不给参考图（123.6/18.74）比给 say-hana 更好——说明模型的默认先验里线是干净的，是**软边参考图把它带糊了**；③ ajicoma 分辨率最高但也线条清晰，结果就好。

**"用文字救"失败**（`line-continuity-fix/`）：在 v6 里加了一段 EDGE TRANSLATION（把柔边翻译成连续线、明确不许靠模糊解决）后，say-hana 段长 100→114.7、noir 98→108，但**端点密度几乎没动**（25.3→25.5、25.5→25.6），kualitas 观感也没变。
**"参考图预处理"也失败**（`line-continuity-refprep/`）：unsharp 提清晰度、再叠加结构线暗化，都只是提高局部对比，**不产生"连续长轮廓"**，对线条连续性无实质帮助。

Sol 对这条的复核（`sol-cases/answer_round4_gpt-5.6-sol.md`）：

- 认定"参考图的边缘语言是主因"这个解读**基本正确**，并指出机制：图像条件携带的是**局部视觉特征**（边界对比度、线宽与连续性、笔触长度/方向/密度、高频纹理与低频色块的比例、哪些边界被强调/省略），而文字是**全局语义约束**；两者冲突时模型通常不会严格执行文字里的"边缘翻译"。软边图实际在告诉模型："这个人应该由柔软、断续、颜料型的边界来表达"。
- 它也指出我这轮实验的**局限**：各参考图不仅边缘语言不同，主体/构图/颜色/纹理也不同，所以只能说"强相关且是主要解释"，不能证明唯一因果；最干净的验证是**固定同一张图**做四版（原图 / 只模糊 / 只强化结构边 / 叠人工连续线），每版 8~16 个样本。
- **要让所有画风都线条连续，它给的方案排序**：① 把"风格参考"和"线条结构控制"**拆开**——先用清晰线稿/文字生成一张「同主体、同构图、同色彩，只强化线条与结构边界」的**锚图**，再用锚图控线条、原软边图控色彩材质（代价：多一次生成/合成，锚图可能带错头发服装，单图接口下锚图会替代原参考导致内容保真下降）；② **结构化预处理链**（轻度去微纹理 → 局部对比 → 提取长距离高置信结构边 → 形态学闭运算连断边 → 删孤立短边 → 以 30~50% 不透明度叠回），**不要把所有 Canny 边涂黑**；③ 提示词只加**可观察的结果约束**（长线、稳定线宽、连续外轮廓、合并碎线、别用碎笔触当结构边界），不要再写大段"把柔边翻译成线"；④ 换有显式结构控制的模型/流程（lineart/canny/soft-edge ControlNet、独立 style 与 structure 权重、mask 局部重绘、先色稿后线稿两阶段）。
- **它也承认有做不到的组合**：同时要求"软边颜料感完整保留 + 所有主体边界变成连续长线 + 不加结构控制或后期合成"是**互相冲突**的。最接近的替代是：**先出软画风色稿 → 单独生成结构线层 → 以低到中不透明度叠加，并对脸、发缘、外轮廓做局部控制**。

## 4.15 Sol 第 6 轮：v5-dual 还能怎么改（say-hana 连贯性 + tid 缺组）

把「源图 / v5-dual / v4 对照 / 改良锚图」四组图发给 Sol，它的判读：

1. **主责在锚图、次责在第二阶段措辞**。v5-dual 确实继承了大形与局部方向（段长 116.7→138.8、长线 0.868→0.898、端点 16.32→15.12），但**没有继承"线条拓扑"**（哪条线从哪开始、经过哪里、在哪结束）。原因：**锚图其实是"低纹理版的完整重绘"，不是结构锚图**——头发仍是大色块、裙褶没有主次线、发束没有标出发根/主干/分叉/发尾。
   say-hana 的具体断点：① 右侧长发在肩以下变成色块，发束不连续；② 腰部以下的裙褶"时断时续"，腰带处消失、裙摆处又出现；③ 胸衣内部线条与肩带偏弱，靠明暗而非线；④ 裙摆与水面的交界没有稳定主轮廓。
2. **它给 5 条改进并排序**：① 加**第三张结构线图**（中灰/深棕、只画主结构线、不填黑、不排线）；② 锚图**只做局部结构增强**（头发/衣服/边缘分区裁剪）；③ **锚图迭代两次**（第二次只修结构断点）；④ 改写第二阶段提示词成**可验证的局部要求**（6~10 条主发束、腰→裙摆连续褶皱等）；⑤ 锚图阶段换 `gpt-image-2.5-flare` 对比。

4. **原理上限（重要）**：水彩厚涂的结构靠色块边界/半透明叠加/边缘渗化/笔触方向，而"线条连贯"要求清晰起点、稳定方向、可追踪中段、明确终点——**两者冲突**。继续加线条约束最终会出现黑描边变多、色块变平、褶皱变漫画线、厚涂感下降。**合理目标不是"所有发丝褶皱都连续"，而是"主结构线连续、次级笔触保留断裂感"**；评估要把「主结构连贯」与「纹理端点密度」拆成两个指标。

1. **「太长」是真的，而且能被复现**：15.6k 字符的请求直接 `ConnectionResetError`（12.1s 内断开），换 5.0k / 1.7k 都正常。虽然官方文档说上限 32,000 字符，但**中转站在这个量级上会断连**，所以现有产物格式在 gpt-image 通道上不可用。
2. **文本生成（不带原图）的线条天然偏弱**（段长 76~82、端点 27~29），比带参考图的路径（同素材照走垫图 ≈ 180）差一大截；**Gemini 重绘能把段长拉 +21~25%、端点压 −31~32%**，但仍不及参考图路径。这正是用户说的"不带原图参考不可能跟原来一样"的量化形式。
3. **描述不能一刀切地砍**：压到 1.2k（P3）会丢内容（换成别的姿势/场景）。要压缩应该**保留"内容锚"**（服装/道具/姿势/镜头）而不是删句子。分析产物里现成就有的 `pixiv_tags`/英文 booru tags 就是最好的内容锚 —— 建议的写法是：
   `prompt_gpt（约 550）+ 一句场景 + tag 列表`，总长度 ≤1,500 字符。我试过这个方案（P5），但**被中转站安全系统拦了**（`safety_violations=[sexual]`，源自这张素材照的连裤袜/抬腿内容），换净化措辞后又撞上一次 SSL 断连；也就是说这张特定的照片在 relay 上属于**高敏感样本**，与提示词写法无关。
4. **Gemini 重绘这一段是工作流里最稳的增益环节**：两版产物的排名、端点和长线都改善，且 v4 固件没有把它们 cel 化。

### 建议落到代码的改造（待确认后实施）

1. **按目标通道选画风文本**：分析产物落盘时若目标是 gpt-image 通道，画风段用 `prompt_gpt`（~550）而不是全量 `prompt`（11k）——`utils/style_gpt.resolve_style_prompt(api_type=...)` 已经具备这个能力，只是分析落盘路径没接。
2. **把长描述压成"内容锚 + 短场景"**：新增一个本地压缩器（不调 LLM）：从 refined 描述里抽「主体/服装/道具/姿势/镜头/光线」短句 + 复用 JSON 里的 tags，输出 600~900 字符；保留完整描述在 JSON 里供 Gemini 通道使用。
3. **给分析产物加长度护栏**：落盘时对 gpt-image 目标强制 ≤2,000 字符并记录一条 warn（超过就有断连风险）。
4. **统一两条落盘路径**（CLI 的 `analysis_pipeline` vs GUI 的 `single_analyzer`）的画风段行为，避免"有的产物带 11k 画风、有的只带 `--ar`"。
5. **高敏感素材照**：这类图（丝袜/抬腿/内衣感）在 relay 上会间歇触发内容审核，建议在生图/重绘前做一次**措辞净化**（不提姿态细节、服装用中性词）并默认走腰以上构图（§4.13 已验证有效）。

## 4.17 Sol 第 7 轮：v4 还能怎么改 → v5 固件（含一个真实缺陷修复）

把 say-hana / noir 的 v4 结果（含头部拼图）和 v4 固件全文发给 Sol，它的判断：

- **v4 已避开旧 cel 固件的主要失败模式**（没把水彩转平涂、肤色/冷暖/材质基本保住），但有两个问题：① 清线收益来自"重新解释边界"而不是严格修复原边界；② **仍会凭模型先验补全内容——say-hana 腹部被凭空加了一只手**，这比线条是否连续更严重。

- **一句话**：**在"必须用 Gemini、且要求保真"的前提下，v4 已接近全图文本重绘的上限**；剩下的提升要靠"禁止补全 + 眼部局部保护 + 遮罩式局部重绘或结构线叠加"。

| tid | v5 重绘 | 230.2 | 11.12 | 0.961 | 0.550 |
| tid | **v5 + 头发局部重绘** | **244.3** | **9.58** | **0.967** | 0.550 |
| tid | v5 + 结构线 0.50 | 255.2 | 9.31 | 0.960 | 0.508 |

**结论**：头发专项局部重绘在**三族的头发带上都有效**（段长 +3~22%、端点密度 −7~20%），noir 收益最大（+22% / −20%）；和"结构线叠加"相比各有胜负（tid 上叠加更强、say-hana/noir 上局部重绘更强），两者可串联。

**顺带修掉一个真 bug**：`utils/post_process.py` 调 `generate_image_repaint` 时没传 `use_detail_suffix=False`，于是把 `prompts/gpt-image-optimize/repaint-detail-suffix.md`（写死 **flat cel shading / bold even-weight continuous outlines**）追加到了 v5 固件后面——等于每张局部重绘都被 cel 指令污染（那一版的指标甚至更高，但画风是错的）。已修，并在 §4.21 的评测里保留了两个版本的数据作对照。

### 区域扩充：整个人物 / 人物（不含面部与手）

原来只有固定比例区（头发/脸/头/裙/上半身/整张），不选整张就只能选上半身，没法"只修人物"或"修人物但别动脸"。现在加两个**动态区域**：

- **`subject`（整个人物）**：`detect_subject_box` 用 GrabCut（中心矩形做前景先验，480px 下采样，3 次迭代）取最大前景连通域 bbox，外扩 6%/4% 以免切掉发梢裙摆；检到可信人脸时把脸并进框内。失败回退 (6%,2%)-(94%,98%)。实测：say-hana `(82,7,1603,2528)`、noir `(47,0,1627,2468)`、tid `(108,0,1624,2450)`——都是"整高 + 左右内缩 5~6%"的合理人物框。
- **`subject_no_face`（人物不含面部）**：同样的人物框送 Gemini 重绘（**脸留在裁切图里当上下文**），但**贴回时把头部/脸区从遮罩里排除**（`feather_blend(..., exclude_boxes=...)` 做反向羽化，脸区像素逐点保留原样）。头部区优先用 Haar 人脸；动漫脸常检不到，则从人物框**上半部居中**推一个头部框（三族实测都落在画面高度 19~20%、宽度约人物框 42%）。Haar 的误检会被丢掉：人脸中心落在画面下半部、或框高 >45% 画面、或不在人物框上半部的，一律不用。

实测（say-hana，v5 产物 → 人物不含面部局部重绘）：脸区像素与原图完全一致，头发/裙子按"整个figure"的要求重绘；成图在 `third-pass/sayhana-subject-no-face.jpg`。回归用例见 `tests/test_post_process.py`（`test_subject_regions_cover_whole_figure`、`test_subject_no_face_excludes_head_band`、`test_feather_blend_keeps_excluded_region_untouched`、`test_local_repaint_subject_no_face_keeps_face_pixels`）。

## 5. 六条结论（含数据支撑）
**观察 1：长度没有硬门槛。**
`usage` 直接给出了证据：`A1`（11,283 字符）→ `text_tokens 2,112`；`H1`（31,000 字符）→ `text_tokens 5,867`；`H2`（40,000 字符）→ `text_tokens 7,575`。
字符数与 text token 严格成正比（约 5.3 字符/token），**没有任何截断迹象**，40k 甚至超过文档的 32,000 也被接受（中转站未做该校验，属于灰区，别依赖）。22 次请求 0 失败。
→ 「gpt-image 不支持那么长的输入」这个假设**不成立**。

**观察 2：长提示词真正伤害的是「参考图的话语权」。**
把参考图固定住、只变文字量（按文本字符数从小到大）：`C（402）≈ C2 → G*（678）→ B5（1855）→ B1（4195）→ B3/B2/B4（13232）→ A1（11k，纯文本）`。
对应 HSV 配色相似度：0.2849 / 0.3186（402）→ 0.2869 / 0.3948 / 0.2579（678）→ 0.1959（1855）→ 0.1055（4195）→ 0.2140 / 0.0572 / 0.2735（13232）→ 0.0151（11k）——**除了 B4 这一个例外，整体单调下滑**；文字越长，输出越往 gpt-image 的默认风格漂：饱和度从 27.4（678 字符）一路涨到 99.3（4195）、94.2（13232）、157.3（11k 纯文本），白底占比从 0.289 掉到 0.025。§4.5 用真实提示词复验过这一点（短说明 0.390 / 全量+图 0.247 / 全量纯文本 0.119）。
→ **几千词的画风说明书在 gpt-image 上是负资产**：它稀释主体、抢走参考图的空间。

**观察 3：本项目四个模式在 gpt-image 上的语义与 Gemini 不同。**
- `interleave`（图文交错）在 Gemini 上是真的 `[text, image, text]` 交错；在 gpt-image 通道里 `build_gpt_image2_payload` 把 `instructions + prompt + post_instructions` **拼成一条字符串**发给 `/images/edits`，图片永远只有一组附件——**交错结构不存在**，等价于「说明放结尾」。
- `priority`（参考优先）名义上"参考图主导"，实测却被压缩版指令里的细节规则牵着走（HSV 仅 0.1055，白底 0.057）。
- `head`（头部插入）把 1.4k 词规则塞在参考说明之后，长文本直接把参考图压掉。
→ 想要「参考图主导」，**唯一有效的做法是缩短文字**，而不是把模式切换来切换去。

**观察 4：参考图是真的在起作用，而且会「过拟合」到主体特征。**
`E1`（一个画风字都不写）与 `B5`（短压缩指令）都把参考图角色的**粉发 + 金瞳**搬了过来；`D_control`（无图无文字）则是黑发 + 深蓝海面的默认半写实。
隔离实验 `G1（有图）↔ G4（无图）`：同一段 678 字符说明，有图 HSV **0.2869** / 白底 **0.289** / 边缘密度 0.0782，无图 HSV **0.2001** / 白底 **0.134** / 边缘密度 0.0891 —— 参考图单独贡献了约 **+0.09 HSV、白底翻倍**，而且无图时边缘更"硬"（回到 2.5D 厚涂的轮廓）。
→ gpt-image-2 的 `input_fidelity` 不可调、所有输入图按高保真处理，**它倾向于把参考图当"要编辑的原图"而不是"风格色卡"**。想只要画风，必须**显式写出「保留什么 / 换掉什么」**（校准版 G 系列就是干这个的）；反过来，只想让参考图出效果、不想写字，就接受它连主体特征一起搬。

**观察 5（顺带）：2.5 两个模型在同样输入下输出更省、画风更稳。**
`G2/G3` 的 `output_tokens` 只有 **343**，而 gpt-image-2 同参数是 **1,105~1,372**（约 1/3）；耗时 flare 29.6s、sunburst 36.0s（都低于 gpt-image-2 的 51.3s）。`G2` 的 HSV 与白底占比还是全组最佳。
→ 走参考图 + 短说明的场景，`gpt-image-2.5-flare` 是当前更优解。

## 6. 给本项目的落地建议

1. **给 gpt-image 通道单独准备一份「短版」画风说明**（目标 **400~700 字符**，参考 `G*` 校准版的写法：保留项 + 更换项 + 一句 scene），不要复用 Gemini 用的 `prompt_compressed`（1,758 字符）和全量 `prompt`（11,186 字符）。可以在 `config-styles.json` 条目里加第三个字段（例如 `prompt_gpt`）或按通道选择，避免在 Gemini 上反向退化。
2. **凡是走 gpt-image 路径，参考图必须配「显式换主体」的短指令**：只写「参考它的画风」不够，实测会连发色/瞳色一起复制。
3. **不要对 gpt-image 用 `head`（全量）与 `interleave` 两种模式**：前者是把长文本压在参考图前面，后者在 payload 层根本不成立。全部塌缩成一条短 prompt 即可。
4. **「无法生图」排查顺序**（按实测概率）：
   - **整包体积**：单图 data URL 上限 20 MB（`maxLength 20971520`），长提示词 + 多张参考图会让 multipart/JSON 请求体越来越大；本项目的 `_maybe_compress_image_path` 只在超 2048px 时压缩，**没有总包体积保护**——这是一条真正可能触发上游拒收的路径；
   - 站点/通道是否支持 `background=transparent`、`input_fidelity`（gpt-image-2 不允许传后者）；
   - 尺寸是否在上游允许清单（aigc2d 只有 3 档，其他值会被收敛，收敛逻辑见 `normalize_gpt_image2_size`）；
   - 参考图是否超 16 张；
   - 内容审核（4xx 会原样落盘，不重试；看 `data/<日期>/<子目录>/*_server_response_*.json` 里的 `error`）；
   - 额度/并发（429/5xx 才重试）、超时（`high` 画质单张 3~5 分钟）；
   - **最后才怀疑提示词长度**——本轮 11k~40k 全部成功，22 次 0 失败，没有复现「长前置词导致拒图」。
5. **量化回归就用这套脚本**：`tests/calc_style_similarity.py`（CLIP+HSV+线条）+ 本目录 `fingerprint.json` 的亮度/饱和/白底口径；改画风注入逻辑后跑一遍，看 HSV↑、亮度↑、白底↑、边缘密度差↓ 是否同向。
6. **模型选择**：参考图 + 短说明走 `gpt-image-2.5-flare`（快、省 token、画风最贴）；要更"重"的厚涂感再试 sunburst；`gpt-image-2` 保留给纯文字生图。
